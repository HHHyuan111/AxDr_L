# 04 开发行为约束（AI 行为升级版）

> 定位：对 00/01/02 号规范的**行为层**补充，约束开发过程本身（改什么、怎么改、怎么验证、
> 怎么交付），而不是代码写法。优先级：与 00 冲突以 00 为准；本文与 01 冲突时，
> 01 是代码执行细则、本文是行为纪律，两者分别管辖。
> 已落成 hook 自动审计（.claude/settings.json + tools/hook_*.py + tools/audit_rules.sh）。

## 1. 核心原则

易读、易懂、易维护，可读性优先于简短。新接触项目的工程师按代码从上到下顺序
就能理解执行步骤和设计原因——这是教学工程的第一标准，与"无 AI 痕迹"同源。

## 2. 修改前先确认范围

1. 先查工作区状态、当前分支和任务基线，保留用户及同事的改动；
2. 先读相关代码和已有流程，不凭印象推断接口、硬件行为或错误原因；
3. 多步任务先列步骤与验证标准；有歧义时说明并提问，同时推进不依赖答案的部分；
4. 有更简单的方法直接提出并说明取舍，不默默引入额外功能或架构。

## 3. 代码写得直接、清楚

1. 普通 if/else、for、提前返回；减少嵌套，主流程保持一条线；
2. 不用复杂三元、隐式技巧、过度压缩；宁可多写几行；
3. 命名表达实际用途。**本项目短名惯例（fb/ref/ia/iq）继续有效**——前提是
   类型定义头部写明单位和含义（00 规范 §3.2），读一次就懂；
4. 不过度拆分：只有职责独立、确有复用、逻辑复杂或表达明确概念时才封装。
   简单校验就地处理；不为了"主函数只留调用"而拆；
5. 不建纯转发包装层、一次性抽象、不必要的配置项或第三方依赖；
6. 优先类型、枚举和普通函数，不为简单表达式堆宏。

## 4. 不做推测性的防御

1. 外部输入在入口按契约校验；内部用已确认的值，不逐层重复检查同一条件；
2. 不为没有实际依据的竞态/边界加锁、关中断、队列、重试或复杂状态；
   确需超出已确认范围的防护，先说明出错路径、发生依据、时序代价，经确认再做；不编造概率；
3. 不以精简为由删除已有保护，或改变释放/异常/并发/实时的正确语义。

## 5. 嵌入式工程习惯

1. 沿用仓库现有目录、命名、模块职责、构建流程（两套地图以 Keil 为主，见 02 §10）；
2. 4 空格缩进禁 Tab；条件/循环必加花括号；头文件保护沿用仓库既有形式（`AXDR_XXX_H`）；
3. 修改处遵循周边风格，不整文件重排；单行 ≤120（严于通用 300）；
4. 注释用简洁准确的中文；公共接口中文 Doxygen（用途、约束、返回值）；
   注释解释目的、设计原因、单位、时序和不明显行为，不逐句复述代码；
5. 高频中断改动关注耗时、栈、内存；避免无谓遍历、数据复制、格式化日志、动态分配；
6. **不手改生成文件**（axdr_build_id.h 只由 gen_build_id.py 生成——hook 审计第 4 项）；
   不顺手改 SDK/第三方库/底层驱动（segger/ 为 vendor 区，免扫描但同样不改）。

## 6. 错误管理（映射到本项目结构）

原文的 components/error_code 是另一项目的结构；本项目等价物是：

| 原文要求 | 本项目落地 |
|---|---|
| 统一管理错误、锁存和现场 | foc_fault_t 位图 + 首故障定格（first_fault_bits/seq）+ ret_e |
| 清单集中维护 | fault.h + axdr_command_contract.h 的 reason 枚举 |
| 检测流程内置位 | 检测方置位（02 §6），Drive 统一停机 |
| 确认恢复的流程内清 | DISARM / drive_fault_clear 显式清除 |
| 不堆业务判断 | 保护函数只判阈值，状态机统一处置 |
| 编号不复用 | 故障位与 reason 码一经发布不复用；改动同步检查恢复/停机行为 |

普通错误置位保持简单；只有定位需要时才填原因/来源/阶段/测量值/限值。
不重复维护旧故障位图，不为每个业务阶段加报错包装函数，不凭空增加检测阈值。

## 7. 只改任务需要的代码

1. 每项改动对应本次需求；不顺手清理无关代码/注释/格式；
2. 重构保持原功能、业务逻辑、接口和异常语义；改行为要明说；
3. 只清理由本次修改造成的未使用项；原有无关问题另行指出（存量规范债清单制）；
4. 未经要求不做兼容层、通用框架、预留功能，不为展示设计模式加复杂度。

## 8. 验证实际行为

1. 用仓库已有工具和流程（host 42 块 + Keil 0E0W + RAM + 真机），不另起测试体系；
2. 测真实实现，不把业务逻辑复制进测试；只替代必要的硬件/平台边界，尽量少用 mock；
3. 重点验证正常流程、真实失败出口、恢复路径、回归场景；纯文本/格式改动不写测试；
4. 严格区分 Host 测试 / 目标编译链接 / 板上观察 / 电机控制验证——**编译通过 ≠ 电机正常**；
5. 相关检查通过后收尾；只有新改动、失败或未解决时才扩大或重复验证；
6. **烧录和电机动作按用户明确指定的对象、参数、范围执行，不得自行触发**
   （已落成 PreToolUse 硬拦截：J-Link loadfile / 强推 / taskkill）。

## 9. Git 与本地文件

1. 新分支命名用 feat//fix/ 等仓库约定，**不用 codex/ 前缀**（存量分支 codex/firmware-validation
   经用户确认后处理，不擅自改名）；
2. 提交说明用简洁中文，写清改了什么、为什么；
3. 个人临时文件用 `.git/info/exclude` 排除，不为此改共享 .gitignore
   （共享构建产物除外——资源产包生成物已入 .gitignore，属项目级约定而非个人文件）；
4. 提交推送由用户授权；推送后核对远端与本地一致、工作区与暂存区状态如实汇报；
5. 改写已发布的本人分支历史：先核实远端，force-with-lease，不覆盖他人提交。

## 10. 交付与敏感信息

1. 先完成实际文件修改，再简要说明改动、原因、验证结果；不只给计划或片段；
2. 用户要求看代码时给完整函数/文件；已改工程用文件链接定位，不重复粘贴整份；
3. 可能影响原有功能或兼容性的修改单独指出；**未运行的验证明确写"未运行/NOT_RUN"**；
4. 不输出、记录、提交任何凭据；示例用占位值；发现疑似泄漏时提醒更换、不复述凭据。

## 附：双 target 构建与产包一致性（本项目特有，本次实战教训）

1. 双 target 共用 axdr_build_id.h；**最后构建的 target 决定头文件内容**；
2. 产包脚本有硬门：头文件 target ≠ 请求产包 target 时拒绝（build_resource_package.sh）；
3. **Release 产包前最后一次构建必须是 AxDr**；Debug 构建后要产 Release 必须先重建；
4. build_id 在镜像里以 movw/movt 立即数存在，**字节模式搜索不可靠**——身份核对用
   反汇编（fromelf --text）或运行时 0x2B 查询，不以 grep 二进制代替。
