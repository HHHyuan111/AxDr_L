# AxDr 支线开发规则

2026年11月2日。汇总用户已认可的代码阅读方式和本轮审核勘误。具体结构、接口与行为修改依照开发计划逐项评审，不把建议直接变成大范围改造。

## 阅读与代码组织

1. 易读、易懂、易维护优先。新接手者能沿代码理解输入、计算顺序和结果；短小算法连续展开，不以代码行数评价质量。
2. 主流程展示反馈、保护/状态、参考生成、控制与输出；各层细节程度接近，不把保护展开很多页却把控制全部藏入空泛调用。
3. 使用普通if/else、switch、for和提前返回。复杂三元、隐式技巧改成直白步骤；普通简单表达式不必机械禁止。
4. 只有独立职责、实际复用、复杂逻辑或真实接口边界才封装。不增加纯转发、多层typedef、一次性函数表和无需求的配置项。
5. 同一模块紧密相关的数据优先放一起，结构体内按配置、运行状态分区。生命周期或写者不同且确有需要再分；不为每个变量造结构体。
6. 控制参数和电机参数集中在项目config及档案；类型、参数值和运行初态分清。派生量由原始参数计算，不维护多个互相漂移的值。
7. cur/ref/fb/iq等工程短名允许使用。公共参数补对象限定；原始ADC、去偏计数、物理电流命名区分。参考、反馈、限值不要混名。
8. 普通段落使用“积分限幅”“输出限幅”等短注释；isfinite、位操作、转换等新手难点补具体解释。必要单位、坐标、周期、状态次序和副作用保留。
9. C默认UTF-8、4空格、条件循环加花括号、一行一条语句、原则上不超过120列；只整理相关代码，不整库重排。公共接口简洁中文说明用途和必要约束。

## 命令与控制

- 协议负责解析和响应，Drive接收目标与模式，控制周期采用；真实接口应包含职责，不为了统一入口新增空转发。
- 用户目标、已采用参考、控制器历史和诊断副本分别说明来源与生命周期。每个运行状态有明确维护者，必要副本说明更新时间。
- 状态、控制模式和执行频率分别处理。采用普通switch和明确分频；切换时规定保留/清除哪些状态，不能仅换枚举。
- 简单数值函数可以直接返回结果；bool/错误码须有明确含义，不把“未到执行周期”当作故障。独立算法的输入/输出结构可保留，不强行全部展平。
- 配置检查在实际入口完成，失败旧值保持；整组并发更新按真实执行上下文保证。内部不重复检查已成立条件；运行中会失效的反馈和故障条件仍需检测。
- 保护检测与处置职责清楚，关断和恢复路径完整。不以“减少防御”为由删掉实际必需的校验、锁存、授权或同步。

## 数值与实时

- 明确单位、坐标系、采样周期、量化、饱和、初值及更新顺序。保持已验证算法的数值语义；改变运算次序或积分形式属于算法变更。
- float适合当前快环的默认实现；长累加等位置按误差与耗时决定，不能不评估就删double。现有辨识实现的精度选择需保留依据。
- 关键路径工作量有界，不阻塞、不动态分配、不格式化日志。检查实际最坏耗时、栈和内存；代码变短不等于更快。
- volatile不保证整组数据一致；单次访问、成组快照、命令发布分别设计。局部数组按生命周期、重入和栈预算选择存放位置。
- 生成文件改生成来源，SDK与第三方不顺手改；原始数据、失败记录和冻结模块保留。

## 原规范勘误

下表在本支线优先采用。原文件保留以便追溯，后续统一规则时再消除重复；未列出的工程约束继续按适用范围执行。

| 旧要求 | 本支线处理 |
|---|---|
| 同层一律禁止调用，通过foc_t字段协作 | 约束职责、依赖方向及循环依赖；允许明确接口调用，不用共享字段隐藏依赖 |
| 改动两个及以上插槽就是破坏架构 | 依功能影响检查算法、配置、通信、测试；跨多个部分本身不是错误 |
| 积分存未乘Ts的和能根治停滞 | 不采用此结论；浮点累加仍有精度限制，按误差和范围选择状态形式并验证 |
| 全项目禁double | 默认快环float；已有长累加等逐项评估精度、频率和资源，不机械改写 |
| 大于64字节局部数组全部static | 按栈预算、生命周期与重入决定；static会改变共享与持久化语义 |
| 32位单值原子即可得到快照一致性 | 单值访问和整组一致性分别判断，明确读写上下文与同步 |
| packed即可得到可靠通信格式 | 另核对字节序、对齐访问、浮点表示、长度及协议版本；不自动改现有协议 |
| 所有算法固定init/reset/tick三件套 | 真实有状态与生命周期才需要对应接口，纯计算不造空函数 |
| RAM不允许上涨、固定测试数视为质量门 | 按实际预算、功能需求及检查内容判断；原有预算保留，新增量要说明 |
| 所有改动均需实机后才能保存提交 | 纯文档按内容/链接/差异检查；固件可保留已验证到实际阶段的提交，明确待实机，不冒充完整验收 |

## 验证与交付

使用仓库既有工具，先检查脚本作用，真实硬件边界才替代。正常、边界、失败和恢复按改动选取；不要把实现复制到测试里自证。检查测试返回值与负例，确保错误能被检测。

Host数值、目标编译链接、资源与实时、实机效果分别报告；未运行写明。文档和纯格式不新增控制测试；通过后收尾，只有新变更或未解问题再扩大验证。

每轮先完成授权范围的工作，再展示完整相关函数或改动与一句原因。用户负责观感反馈，开发方负责技术正确性。存在真实取舍时给2—3种行为一致的写法，不反复问已确认偏好。

## 分支与范围

仅在本支线工作；保留原分支和他人修改。行为修复与可读性整理分开，提交只含相关文件。此次允许创建并推送计划分支；后续发布、合并、烧录和运动按新任务授权执行。不把原项目路径、固定平台参数或项目约束扩散成通用知识库规则。
