# 状态机动作与状态判断分离

## 本节点要解决什么

旧版 `pmsm_run_state_machine()` 在一个 `switch` 分支里同时完成三类事情：

1. 执行启动、停止或运行；
2. 判断动作完成后的状态；
3. 发现故障后安排下一周期复位。

代码功能没有错，但“现在要做什么”和“做完后处于什么状态”混在一起，不便于阅读和后续把 Drive 层独立出来。

本节点只拆分职责，不新增状态，不修改状态值，也不改变任何硬件动作。

## 改完后的大白话流程

```text
读取本周期入口的 ctrl_bit，保存为 ctrl_req
    ↓
pmsm_exec_action()
    ├─ start：启动 PWM → 写 50% → 清控制器
    ├─ reset：停止 PWM → 清控制器
    └─ opera：执行当前选定模式
    ↓
pmsm_eval_state()
    ├─ start：无故障为 prech
    ├─ reset：无故障为 stop
    └─ opera：无故障为 runing
    ↓
故障最终覆盖为 fault
    ↓
状态为 fault 时，把下一周期请求改为 reset
```

## 为什么需要 ctrl_req

`ctrl_req` 是进入本周期状态机时对 `ctrl_bit` 的一次本地保存。

快速停车、故障停车、标定或辨识流程可能在运行途中把 `pm->ctrl_bit` 改成 `reset`，意思是“下一周期去复位”。但是当前周期已经是按 `opera` 进入并执行的，当前周期的结果状态仍应按 `opera` 判断。

如果动作执行完后重新读取 `pm->ctrl_bit`，就会把当前周期错误地当成 `reset` 分支。保存入口请求与 C 语言原有 `switch (pm->ctrl_bit)` 只在入口求值一次的行为一致。

## 两个私有函数分别负责什么

### pmsm_exec_action()

只执行动作，不写 `state_bit`：

- `start`：保持“启动三相输出 → 写三路 50% → 清控制器”的原顺序；
- `reset`：保持“停止三相输出 → 清控制器”的原顺序；
- `opera`：调用 `pmsm_run_selected_mode()`；
- 未知请求：不执行动作。

### pmsm_eval_state()

只写 `state_bit`，不启停 PWM，不调用控制算法：

| 入口请求 | 无故障结果 | 有故障结果 |
|---|---|---|
| `start` | `prech` | `fault` |
| `reset` | `stop` | `fault` |
| `opera` | `runing` | `fault` |
| 未知请求 | 保持原状态 | 最终故障规则仍可覆盖为 `fault` |

公共入口最后仍保留两条原规则：故障具有最终优先级；最终状态为 `fault` 时，下一周期请求为 `reset`。

## 修改范围

仅修改 `foc_ctrl.c`：

- 新增两个 `static` 私有函数，没有扩大公开接口；
- `pmsm_run_state_machine()` 改为“保存入口请求 → 执行动作 → 判断状态 → 故障最终处理”；
- 枚举、结构体、运行模式、控制算法和 Target 接口均未修改。

两个私有函数和公共状态机入口都保留在 `.RamFunc` 输入段，并链接到 RAM 地址执行。

- Release clean-first 构建：0 错误，104 个既有警告，无警告增量；
- Host C11 / FOC 数学回归：通过；
- `pmsm_exec_action()`、`pmsm_eval_state()`、`pmsm_run_state_machine()` 均确认位于 RAM 地址区；
- 本节点没有烧录、带电或电机运行测试。
