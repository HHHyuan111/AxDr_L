# Drive 最小状态闭环

## 一句话说明这次改了什么

上电后不再直接打开三相 PWM；Drive 层收到一次 `START` 请求后只启动一次，下一快速周期自动进入 `RUN`，收到 `STOP` 或发现已有故障时关闭三相 PWM。

这一步只把“什么时候启动、什么时候运行、什么时候停止”理顺，没有修改 FOC 公式、控制参数、采样顺序和运行模式映射。

## 大白话流程

```text
系统上电
    ↓
三相 PWM 保持关闭，Drive 停在 STOP
    ↓
外部把 pm.req 写成 DRIVE_REQ_START
    ↓
第 1 个快速周期：启动三相 PWM → 写三路 50% → 清控制器
    ↓
本周期结束：状态为 STARTING，请求自动改为 RUN
    ↓
第 2 个快速周期：执行当前选定的运行模式
    ↓
模式内部调用 FOC，计算成功后经 Target 提交 PWM
    ↓
后续每个快速周期继续 RUN，直到收到 STOP 或发现故障
```

`START` 和 `RUN` 不是一回事：

- `START` 只负责把硬件和控制器带到统一起点，只执行一个快速周期；
- `RUN` 才会反复执行电流环、速度环、位置环、MIT 或当前选定的其他模式。

## 请求、状态和 PWM 记录分别表示什么

| 字段 | 大白话含义 | 谁主要修改 |
|---|---|---|
| `pm.req` | 下一次快速周期想做什么：停止、启动或运行 | 后续命令入口、标定/辨识结束逻辑、Drive 自动转换 |
| `pm.state` | 这一次动作做完后，电机控制实际处于什么阶段 | Drive 层 |
| `pm.pwm_active` | 软件是否已经发出三相 PWM 启动动作 | Drive 层 |

`pwm_active` 不是从定时器寄存器读回来的硬件真值，也不是新的保护系统。它只用来避免在 20 kHz 快速周期里反复调用同一个 PWM 启动或停止函数。

## 当前状态闭环

| 本周期入口请求 | 入口 PWM 记录 | 本周期动作 | 无故障时的结果 | 下一请求 |
|---|---:|---|---|---|
| `STOP` | 关闭 | 不重复调用停止接口 | `STOP` | `STOP` |
| `STOP` | 开启 | 停止 PWM，清控制器 | `STOP` | `STOP` |
| `START` | 关闭 | 启动 PWM，写 50%，清控制器 | `STARTING` | 自动变为 `RUN` |
| `RUN` | 开启 | 执行当前选定模式 | `RUN` | 保留实时请求 |
| `RUN` | 关闭 | 不运行控制模式 | `STOP` | 强制变为 `STOP` |
| 任意请求 | 任意 | 先完成本周期入口动作，再汇总故障并停止 PWM | `FAULT` | 强制变为 `STOP` |

模式内部如果在本周期把请求改成 `STOP`，Drive 不会把它覆盖回 `RUN`。当前 RUN 动作执行完，下一快速周期再执行停止，这与旧 `switch` 在入口锁存请求的行为一致。

## Drive 文件里的函数分别做什么

### `drive_fast_step()`

这是 Drive 层唯一公开的快速入口。它按固定顺序完成四件事：

1. 保存本周期入口请求；
2. 执行这个请求对应的动作；
3. 汇总 `fault.all` 并在需要时关闭 PWM；
4. 更新状态，并把成功的 `START` 自动转成下一周期的 `RUN`。

### `drive_start_pwm()`

仅在软件记录为未启动时执行一次启动过程。内部顺序保持旧代码不变：

```text
foc_pwm_start()
    → foc_pwm_duty_set()，写三路 50%
    → pmsm_reset()，清 PI 和控制目标历史量
```

### `drive_stop_pwm()`

仅在软件记录为已启动时执行一次停止过程：

```text
foc_pwm_stop()
    → pmsm_reset()
```

### `drive_exec_action()` 与 `drive_update_state()`

- `drive_exec_action()` 只决定本周期做 STOP、START 还是 RUN 动作；
- `drive_update_state()` 只根据动作结果写 `STOP`、`STARTING` 或 `RUN` 状态。

它们都是文件内私有函数，没有扩大外部接口；Debug ELF 中也确认位于 RAM 执行区。

## 在完整快速链里的位置

```text
ADC1 注入转换完成回调
    ↓
fast_loop_step()
    ├─ 读取编码器原始值
    ├─ 更新机械角和电角度
    ├─ 读取并换算 ADC
    ├─ 更新速度、转矩和观测反馈
    └─ drive_fast_step()
           ├─ 判断 STOP / START / RUN
           └─ RUN 时调用 Drive 私有的模式分派函数
                    └─ 选定模式调用 FOC
                             └─ 计算成功后经 Target 提交 PWM
```

TIM1 CH4 仍在 `main.c` 中启动，因为它负责触发 ADC 采样和电流零偏流程；它不是三相功率输出。被移除的是 `main.c` 中对 CH1～CH3 三相输出的无条件启动。

## 当前怎样发出 START

仓库目前没有已实现的 CAN、UART 或 USB 运行命令解析，因此上电后会安全地一直停在 `STOP`。现阶段可由调试器把全局对象的 `pm.req` 改成 `DRIVE_REQ_START` 来验证状态链。

本节点没有猜测通信协议，也没有新增一个暂时无人调用的命令 API。正式命令入口应在后续通信边界明确后单独接入。

## 为了通过构建还处理了什么

新增 `drive.c` 后，旧 `common.h` 对工具链数学宏 `M_PI` 和 `M_2_PI` 的重定义会新增两条警告。为消除真实名称冲突：

- 项目自己的 π 常量改名为 `AXDR_PI`；
- 三处把错误命名为 `M_2_PI` 的 2π 用法统一为项目原有的 `M_2PI`；
- 所有常量数值保持完全一致，没有改算法结果。

## 这一步明确没有完成的事情

- 没有接入 CAN、UART 或 USB 的正式 START/STOP 命令；
- 没有把尚未启用的 `pmsm_fault_check()` 接入快速周期；
- 没有增加复杂的预充、故障恢复或硬件保护状态；
- 没有修改电流环、速度环、位置环、MIT、标定或辨识算法；
- 没有修改角度与 ADC 的采样先后；
- 没有烧录、带电或驱动电机。

## 后续硬件验收必须确认的两点

1. 为保持旧时序，START 仍是“先使能三相输出，再写 50%”。需要用示波器确认启动瞬间是否短暂输出旧 CCR 占空比。
2. 为保持阶段 1 的顺序，Drive 仍是“先执行本周期动作，再汇总故障”。已有故障时可能先执行一次 START 或 RUN，再在同一快速周期末关闭输出；是否调整为故障入口优先，需要在硬件安全策略明确后单独决定。

这两点在离线测试中已按当前真实行为锁住，但离线测试不能代替 Gate 和三相波形实测。
