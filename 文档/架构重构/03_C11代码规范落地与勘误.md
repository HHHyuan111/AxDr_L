# C11 代码规范落地与勘误

文档状态：适用于新增代码和本次明确修改的代码，待用户确认格式细节

## 一、适用范围

本文件依据 `课程目录及开发计划/代码规范1.md` 整理，不使用已排除的架构预研材料。

| 代码范围 | 执行方式 |
|---|---|
| 项目自有 C11 模块 | 新增和修改部分执行完整规则 |
| STM32Cube 的用户代码区 | 执行 |
| STM32Cube 自动生成区 | 不做纯格式化修改 |
| `Drivers` 和 `Middlewares` | 按第三方代码处理，不批量整改 |
| 历史工程 | 只修复影响构建、安全或验证的确定性问题 |
| 主机测试代码 | 遵守同样的类型、边界、所有权和错误处理规则 |

质量优先级为：正确性、安全性、可测试性、可读性、整体效率、局部效率。

不要在架构迁移中顺手格式化或重命名整棵旧代码树。

## 二、立即执行的规则

### 排版

- 文件使用 UTF-8，并以换行符结束。
- 缩进为 4 个空格，禁止制表符和行尾空格。
- 单行原则上不超过 120 个字符。
- 一行只写一条语句。
- `if`、`for`、`while` 和 `do` 即使只有一条语句也必须加花括号。
- 逗号和分号后留空格；二元操作符两侧留空格；`.`、`->` 和一元操作符附近不额外留空格。

### 命名

- 函数、变量、结构体和枚举使用英文小写加下划线。
- 公开函数使用模块前缀，例如 `motor_`、`encoder_`、`replay_`。
- 宏和枚举值使用大写加下划线，并包含模块或类型前缀。
- 布尔变量直接表达状态，不使用含义不清的 `flag`。
- 单字符变量只允许用于很小范围的循环。
- 物理量通过名称或注释明确单位，例如 `speed_rad_s`、`bus_voltage_v`、`sample_period_s`。

### 类型和数值

- 寄存器、协议、存储和定点数据使用 `<stdint.h>` 固定宽度类型。
- 数组长度和对象大小使用 `size_t`。
- 布尔值使用 `<stdbool.h>` 中的 `bool`。
- `float` 常量添加 `f` 后缀。
- 有符号/无符号转换和窄化转换必须检查范围。
- 分母可能为零时必须保护；控制算法还应定义接近零阈值。
- 饱和、限幅、角度归一化、积分器边界、NaN 和 Inf 行为必须定义并测试。
- 传输和持久化不依赖结构体填充，显式定义字段宽度和字节序。

### 状态、所有权和接口

- 严禁读取未初始化变量。
- 模块私有对象和函数使用 `static`。
- 新的可变状态必须进入显式上下文，不新增可写全局单例。
- 跨模块共享对象尽量只有一个创建者和写者。
- 只读输入使用 `const`。
- 接口说明输入、输出、单位、范围、所有权、有效性和失败行为。
- 头文件可独立包含，并使用包含保护。
- 头文件不定义具有外部链接的可写对象；大型常量表在 `.c` 中定义，在头文件中使用 `extern const` 声明。

### 宏

- 宏参数和完整结果加括号。
- 宏实参不得包含自增、自减或其他副作用。
- 优先使用 `static inline`。
- 无法避免的多语句宏使用 `do { ... } while (0)`，不能使用裸花括号。
- 离散状态使用枚举，固定物理常量使用有类型只读对象，可调参数进入参数包，不把所有数值都强制做成宏。

### 中断和实时执行

- 中断服务和快速周期必须具有可测量的最坏执行时间。
- 中断中禁止动态内存、文件操作、Flash 擦写、阻塞等待、长循环和无界日志。
- `volatile` 不能替代同步，只用于寄存器或确实被异步修改的对象。
- 中断与主循环共享的多字节状态使用短临界区、原子快照或经过验证的原子操作。
- 快速中断不得等待线程锁、队列或外设完成。
- 任何改变 PWM、Gate、保护阈值或运行模式的输入必须验证。

### 控制流与错误处理

- `switch` 必须有明确的 `default`；每个分支显式 `break`、`return` 或注明贯穿。
- 返回值的所有路径都要完整，调用方检查可能失败的结果。
- 指针使用前建立有效性契约，可空边界显式检查。
- 数组访问前验证长度和索引。
- 不返回局部对象地址，不保存超出生命周期的指针。
- `goto` 不用于一般流程控制；主机工具可在单一资源清理路径中受控使用。

### 注释和文件头

- 新 `.c` 文件至少包含 `@file` 和 `@brief`。
- 复杂或公开函数说明目的、参数、返回值、单位、前置条件和实时约束。
- 注释解释“为什么”和非显然约束，不重复代码表面行为。
- 修改代码时同步更新注释并删除失效的注释代码。
- 英文优先；需要准确表达领域问题时允许使用 UTF-8 中文。
- 不用“注释占比 20%”作为自动化门槛。

## 三、原规范中的矛盾和错误示例

以下内容不应机械照抄：

1. 长表达式同时要求操作符放在续行开头和上一行结尾，并要求普通语句使用反斜杠。普通 C 表达式自然换行，反斜杠只用于预处理宏。
2. 函数左花括号位置在文字和示例中互相矛盾，需要项目格式化配置统一。
3. 某个“正确”单行 `if` 示例没有花括号，与前文强制花括号冲突。
4. `val2` 范围示例的上、下界都写成 `MAX_VALUE_SECOND`，下界显然应为 `MIN_VALUE_SECOND`。
5. 提交说明文字要求空行和编号，但示例没有遵守；当前也没有 Git 仓库。
6. 文档既允许 UTF-8 中文，又在另一处要求只能使用英文注释。本项目解释为英文优先、中文用于提高准确性。
7. `int get_curr_status(0;` 是无效 C 语法。
8. 多语句宏的裸花括号在 `if/else` 中不安全，应改为 `static inline` 或 `do/while (0)`。
9. 文档把未初始化指针和空指针混为一谈。正确规则是先建立有效对象或显式空值，再在边界验证。
10. 部分动态内存“修正”示例在正常路径仍未展示释放；C 中也不需要转换 `malloc` 返回值。
11. 第一版数组边界修复仍允许编号为零时访问负下标。
12. `vector`、指针引用和 `const int&` 属于 C++，不适用于生产 C11。
13. 普通 `char` 是否有符号由实现决定，不能用它修复无符号循环下溢；需要明确范围时使用固定宽度类型。
14. 返回字符串字面量应使用 `const char *`，不能暴露为可写 `char *`。
15. 双重指针分配示例赋值给了 `p` 而不是 `*p`；目标机实时路径原则上也不应引入堆。
16. 桌面线程锁规则不能直接移植到快速中断，阻塞锁可能导致死锁或破坏实时性。
17. 删除元音造缩写、给变量编码类型、所有物理量强制宏化和注释百分比都不作为项目机械规则。

## 四、需要确认的格式细节

在建立自动格式化规则前，需要确认：

- 函数左花括号同行还是另起一行；
- 长表达式的操作符放在上一行末尾还是下一行开头；
- 类型名是否统一使用 `_t`；
- 枚举值是否统一使用“模块、类型、值”的完整前缀；
- 文件头是否只保留 `@file/@brief`，将作者、版本和日期交给版本控制；
- 注释是全英文，还是英文优先、中文补充；
- 调试版和发布版的断言及非法输入处理；
- 主机工具是否允许动态内存及其独立规则；
- 何时对项目自有代码启用警告视为错误、静态分析和覆盖率门。

## 六、落地步骤和验收

1. 先建立编码配置和检查命令，不立即格式化旧代码。
2. 优先修复未初始化、类型不匹配、缺失返回、越界、空指针和除零问题。
3. 格式整理和功能修改分开。
4. 新增及明确修改的代码先达到规范，存量代码按模块迁移。
5. ARM GCC 和 ArmClang 同时检查项目自有代码。
6. 项目自有代码警告清理后，再逐步启用警告视为错误；第三方和生成代码单独处理。
7. 每条安全规则至少对应一个构建检查、静态检查或测试用例。

完成条件：

- 从空构建目录生成 ELF、HEX 和 MAP；
- 项目自有代码在 ARM GCC 和 ArmClang 下无错误、无新增警告；
- 不存在已知的未初始化读取、缺失返回和类型不匹配；
- 公开接口具有单位、范围、所有权和错误行为说明；
- 实时函数没有动态分配、阻塞和无界执行路径；
- 格式化不改变固件行为，算法变化均有数值测试依据。
