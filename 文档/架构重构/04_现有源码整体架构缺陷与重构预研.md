# 现有源码整体架构缺陷与重构预研

文档状态：只读预研结论，尚未实施源码修改

分析日期：2026-08-27

## 一、分析范围与结论性质

本次只分析当前主固件工程：

    AxDr原始代码/AxDr_L-main/AxDr_App

用户已确认误传的“代码架构预研.md”继续排除，本文没有采用其中的目录、接口、结论或验收数字。

本文依据现有 C 源码、头文件、STM32Cube 生成配置、Keil 工程和历史链接映射文件得出。本文提出的目标类型、接口和迁移顺序属于新的工程建议，不代表这些接口已经冻结。

本轮未修改原始源码、工程文件和构建配置。

## 二、先给结论

当前代码不是简单的“变量名不够规范”，而是四个问题叠加：

1. 数据职责没有分开。配置、命令、反馈、控制器历史状态、算法临时量、故障、标定、辨识、显示和查表数据都集中在一个全局对象 pm 中。
2. 数据所有权不明确。多个模块直接读写 pm；部分算法又在 pm 外维护第二份全局变量或函数静态变量。
3. 调试能力进入了控制语义。debug_mode 不是单纯开启日志或观察，而是直接选择开环、电流、速度、位置等功率控制路径。
4. 算法、板级驱动和通信显示没有稳定边界。common.h 把 HAL、BSP、硬件宏、全部类型和全部算法接口绑在一起，导致纯算法无法脱离 STM32 环境独立编译、回放和测试。

从成熟控制固件的角度，当前代码更接近“通过调试器选择实验并直接观察全局变量的算法实验固件”，还不是“可安全启停、可重复验证、可多实例运行、可离线回放的算法复现平台”。

用户对调试结构体耦合严重的判断是准确的，但实际情况还有一层：现有 pmsm_display_t 虽然复制了大量控制数据，却没有形成真正的一致快照；LCD 没有消费它，VOFA 又绕过它直接读取 pm。因此当前方案同时承担了额外耦合和重复存储，却没有获得可靠的调试隔离。

## 三、当前源码架构

### 3.1 当前运行链路

    main
      ├─ 初始化 HAL、ADC、TIM、SPI、USB、UART、FDCAN、LCD
      ├─ 启动 ADC 注入转换中断和 TIM1 触发
      ├─ 调用 pmsm_init 初始化全局 pm
      └─ 进入基本空闲的主循环

    20 kHz ADC 中断回调
      ├─ 轮询 SPI 读取编码器
      ├─ 计算位置和角度来源
      ├─ 读取 ADC 并换算电流、母线及派生量
      ├─ 运行速度、观测器和控制器
      ├─ 在多层模式分支中选择实验或控制路径
      └─ 直接启动、停止或更新 TIM1 PWM

    显示和遥测
      ├─ pmsm_ctrl_display：计划把 pm.foc 复制到 pm.display，但当前调用被注释
      ├─ display_foc：显示固定常数，没有读取 pm.display
      └─ vofa_start：绕过 pm.display，直接读取 pm.adc 和其他 pm 内部字段

### 3.2 当前依赖形态

    绝大多数电机算法源文件
      ↓
    common.h
      ├─ 标准库
      ├─ main.h
      ├─ bsp.h
      ├─ HAL 和板级符号
      ├─ PWM、SPI 片选等硬件宏
      ├─ 全部公共结构和枚举
      ├─ 全部算法函数声明
      └─ extern pmsm_t pm

    各算法、状态机、标定、辨识、显示、遥测
      ↔ 直接读写全局 pm
      ↔ 部分模块再维护额外全局或静态状态

这个依赖图没有形成“上层依赖下层接口”的单向关系，而是以 common.h 和 pm 为共享内存总线。只要某个字段移动、改名或改变更新时刻，大量不相干模块都会受到影响。

## 五、成熟框架视角下的核心缺陷

### 5.1 巨型全局对象同时充当数据库和消息总线

证据：

- User/motor/foc_drv.c 第 3 行定义全局 pm。
- User/motor/common.h 第 1377 至 1428 行的 pmsm_t 聚合模式、板卡、ADC、参数、命令、控制、FOC、显示、周期、保护、位置、标定、辨识、齿槽补偿、多个观测器、五个 PID、八个滤波器、轨迹和查表数据。
- MDK-ARM/AxDr/AxDr.map 第 5204 行记录 pm 为 50,232 字节。

影响：

- 任何模块都可能跨层修改内部状态。
- 无法回答“这个字段由谁写、何时有效、允许谁修改”。
- 现有完整运行链无法可靠地并行运行两个独立实例做 A/B 算法对比。
- 无法保证复位一个算法时，其函数静态状态也被复位。
- 现有端到端回放仍需携带硬件相关对象和依赖；部分纯计算函数可以单独测试，但尚未形成独立算法库边界。
- 修改结构体布局会造成大面积重新编译和潜在行为变化。

建议：

- 短期不立即删除 pm，而是先把它限制在应用装配层，作为兼容外壳。
- 每迁移一个模块，就为其建立显式的配置、状态、输入、输出和诊断对象。
- 最终让算法函数只修改自己的 state 和显式 output，不再隐式访问 pm。
- 大表、标定工作区和辨识会话不再无条件常驻每个电机实例。

### 5.2 配置、状态、输入、输出和调试量混装

典型例子是 pid_para_t：

- kp、ki、kd、周期和限幅属于配置。
- i_term、历史误差属于可变状态。
- ref、反馈、P/I/D 分量和 out 属于本周期输入、输出或诊断。
- 所有字段统一使用 volatile。

volatile 只能约束编译器的部分访问优化，不能提供多字段的一致快照、原子更新或线程/中断同步。字段能够被调试器或其他模块随时修改的根因，是全局对象缺少封装、只读限定和所有权边界；统一添加 volatile 没有解决这个问题，反而模糊了配置、运行状态和并发数据之间的区别。

建议拆为：

    pid_config_t
      增益、周期、限幅、抗积分饱和策略

    pid_state_t
      积分状态、历史误差、历史反馈

    pid_input_t
      本周期参考和反馈

    pid_output_t
      控制输出和饱和状态

    pid_diagnostics_t
      P/I/D 分量、限幅原因、非有限数状态

同样的拆分原则适用于 FOC、观测器、保护、标定和辨识模块。

### 5.3 数据存在多写者，参数更新没有事务边界

证据：

- foc_drv.c 初始化和更新电机参数。
- idpm.c 辨识过程直接覆盖 pm.para，并立即重算部分控制器。
- 状态机、辨识和初始化路径都能修改控制模式和运行状态。

影响：

- 未收敛或异常的辨识结果可能直接进入在线闭环。
- 一组相关参数可能只更新了一部分。
- 运行周期无法知道本周期使用的是旧参数、部分新参数还是完整新参数。
- 没有候选、校验、批准、回滚和来源追溯。

建议建立：

    辨识会话
      → 候选参数结果
      → 范围、单位、一致性和稳定性校验
      → 离线回放或仿真验证
      → 在安全状态显式提交
      → 原子切换活动参数版本
      → 保留上一版本以便回退

运行参数只能由参数服务写入，辨识器和自整定器只能提交候选结果。

### 5.4 算法状态存在第二份所有权

源码中除了 pm 还存在：

- alob.c 的全局 alob，而 pm 中又嵌入 pm.alob。
- hfsi.c 中的 hfsi 及多组游离全局变量。
- eh_observer.c 中的全局观测器对象。
- idpm.c 中的全局数组和大量函数静态变量。
- foc_drv.c 中的速度测量函数静态历史状态。

其中 alob 已出现“初始化全局 alob、运行 pm.alob”的对象不一致路径。该问题不只是风格问题，会导致运行实例没有收到预期指针和参数。

建议：

- 所有可变算法状态进入调用者持有的显式上下文。
- init、reset、step 始终作用于同一上下文。
- 真正不可变的查表数据可以保留为文件内 static const。
- 测试必须验证两个实例并行运行互不影响，单独复位互不污染。

### 5.5 硬件边界和纯算法边界不存在

证据：

- common.h 直接包含 main.h 和 bsp.h。
- common.h 中定义 TIM PWM 和 SPI 片选宏。
- foc_drv.c 直接操作 ADC、TIM 和 HAL。
- encoder.c 把 SPI 访问与编码器算法状态混在一起。
- 控制模式函数内部可以直接启停或写 PWM。

影响：

- FOC、PID、观测器、位置估算和辨识无法在主机环境直接复用。
- 离线回放必须模拟 HAL 或重写一份算法。
- HIL 和板级固件难以共享同一生产算法源。
- 安全限幅和最终实际输出没有唯一责任方。

建议：

- 板级层独占 ADC、编码器总线、PWM、Gate 和 Break。
- 运行引擎只接收完整测量帧，输出逆变器请求。
- 板级安全层拥有最终否决权，并返回实际采用的占空比和 Gate 状态。
- 算法目录不能包含 HAL、寄存器、LCD、USB、FDCAN 或板卡头。

### 5.6 20 kHz 中断承担过多工作

当前中断路径包含阻塞式 SPI、位置处理、电流和参数计算、观测器、控制器、状态模式选择及 PWM 操作。显示、故障和 VOFA 调用虽然当前被注释，但仍被设计在同一回调附近。

影响：

- 最坏执行时间未知，无法证明满足 50 微秒预算。
- 通信、显示或增加一个算法就可能引入电流环抖动。
- 多速率逻辑散落在各算法内部计数器中。
- ADC、TIM、FDCAN、USART、DMA 和 USB 多个中断配置相同优先级，实时优先级关系不清楚。

建议：

- 快环只保留采样锁存、必要估算、控制计算、安全检查和输出提交。
- 1 kHz、100 Hz 和后台任务由统一调度器产生触发。
- 记录每周期开始、结束、超时和最大执行时间。
- 通信编码、屏幕刷新、参数保存和统计处理离开快环。

### 5.7 状态、模式、实验和调试是同一个维度

当前 pmsm_t 同时维护 ctrl_bit、state_bit 和 mode_ctrl_e；其中 mode_ctrl_e 又混合系统用途、控制路径、标定和停机模式。具体表现为：

- 与 mode_ctrl_e 并列的 ctrl_bit 和 state_bit 构成两套启停状态。
- sys_mode 中的 debug、release、calibration、halt。
- debug_mode 下的开环、电流、速度和位置闭环选择。
- release、calibration、辨识等其他控制流程。

这意味着“调试”不只是观察能力，而是改变功率控制行为。默认初始化又把 sys 设置为 debug_mode，把 debug 设置为 curr_cl，其他模式靠修改源码注释或调试器变量选择。

成熟框架应拆成互相正交的维度：

| 维度 | 示例 |
|---|---|
| 功率生命周期 | DISABLED、READY、RUNNING、FAULT_LATCHED |
| 控制模式 | VOLTAGE、CURRENT、TORQUE、SPEED、POSITION |
| 实验流程 | NONE、CALIBRATION、IDENTIFICATION、ANTICOGGING |
| 位置来源 | ENCODER、HALL、OBSERVER、OPEN_LOOP |
| 诊断配置 | 状态快照开关、采样字段、分频、触发条件 |

诊断配置不得改变控制模式、取消保护或直接启用功率级。调试版本可以增加断言和跟踪，但不能改变安全默认值和状态转移含义。

### 5.8 命令模型只是占位，实际没有闭环

pmsm_cmd_t 只有少量浮点设定值，没有：

- 命令序号；
- 发布时间和超时；
- 来源；
- 控制模式；
- 使能意图；
- 有效字段；
- 限制条件；
- 完整提交标记。

源码中没有发现稳定的命令写入路径。USB 接收只重新挂接接收缓冲区，FDCAN 回调为空，pmsm_ctrl_set 的调用也被注释。

建议把命令做成一次完整事务：

    motor_command_t
      命令序号
      发布时间或周期号
      来源
      期望生命周期
      控制模式
      目标值
      限制
      超时
      有效掩码

通信模块只能提交完整命令到邮箱；快环在周期边界一次性锁存，不允许边接收边读取半包字段。

## 六、变量命名和数据模型问题

### 6.1 当前命名为什么会阻碍架构演进

命名问题主要不是“长短”，而是缺失五类语义：

1. 物理单位：A、V、rad、rad/s、rpm、count、摄氏度或标幺值。
2. 坐标系：abc、αβ、dq。
3. 机械位置：转子轴、减速器输出轴或负载侧。
4. 数据阶段：原始采样、标定后反馈、滤波值、估计值、指令值或实际采用值。
5. 时间和有效性：属于哪个周期、是否新鲜、是否有效。

例如：

- pm.adc.ia 看起来像安培，实际更接近 ADC 原始计数。
- pm.foc.i_a 才是换算后的相电流，但名称没有单位。
- we、wr、wm 无法仅凭名称确认电气速度、转子机械速度和输出轴速度。
- sp_r、mp_r、sp_m、mp_m 的单圈、多圈、轴侧和单位只能依赖上下文猜测。
- p_e、e_pr、e_pm、e_pe 难以判断角度来源和方向。

### 6.2 明显拼写和风格问题

当前可见问题包括：

- peroid，应为 period。
- senless，应为 sensorless。
- runing，应为 running。
- calibrat，应为 calibration 或 calibrating。
- opera、prech 等含义和状态不完整。
- FALG、OFFSTE、MIN_MAX_LIMT 等拼写错误。
- fback_value 和 fdback_value 混用。
- spd_measure_M 混合大小写。
- moldue 目录和 modlue.h 拼写错误。
- 枚举值 reset、start、Hall、Nlob 等大小写和前缀不统一。

### 6.3 建议命名规则

- 新代码统一 snake_case。
- 类型统一使用明确后缀，例如 motor_command_t、pid_state_t。
- 枚举值带模块前缀并全大写，例如 MOTOR_STATE_RUNNING。
- 跨模块物理量增加单位后缀。
- 原始采样明确使用 raw 或 counts。
- 估计、滤波、参考和实际采用值必须在名称中区分。
- 禁止用 flag 代替具体含义；用 sample_ready、fault_latched、command_valid 等状态名。
- 不在本轮做全量字符串替换。先确认真实语义，再建立旧字段到新词汇的映射。

建议的初始映射示例：

| 当前名称 | 暂定建议名称 | 备注 |
|---|---|---|
| pn | pole_pair_count | 类型应为经校验的整数 |
| Rs | stator_resistance_ohm | 需确认温度基准 |
| Ld | d_axis_inductance_h | 需确认测量工况 |
| Lq | q_axis_inductance_h | 需确认测量工况 |
| Js | rotor_inertia_kg_m2 | 需确认是否折算负载 |
| pm.adc.ia | phase_a_current_raw_counts | 原始 ADC 计数 |
| pm.foc.i_a | phase_a_current_a | 标定后的物理量 |
| pm.foc.i_d | d_axis_current_a | dq 坐标 |
| pm.foc.p_e | electrical_angle_rad | 需确认正方向 |
| pm.foc.we | electrical_angular_velocity_rad_s | 需源码和实测复核 |
| pm.foc.dtc_a | phase_a_duty_pu | 标幺占空比 |
| Tmos | mosfet_temperature_c | 建议统一小写 |

## 七、调试、显示和 VOFA 耦合专项

### 7.1 pmsm_display_t 是重复镜像，不是一致快照

pmsm_display_t 在 common.h 第 557 至 589 行复制母线、电流、位置、速度、温度和转矩等 FOC 数据。

pmsm_ctrl_display 在 foc_ctrl.c 第 471 至 509 行从 pm.foc 逐字段复制并做符号和角度换算，但其在快速回调中的调用已被注释。源码搜索未发现其他稳定消费者。

问题：

- 字段和 pm.foc 重复，增加存储和同步成本。
- 多字段逐项复制没有版本号，消费者无法判断是否读到完整同一周期。
- 复制函数混入显示方向和角度换算，展示策略反向污染控制数据定义。
- 更新调用被注释后，结构仍留在核心对象中，形成失效耦合。

建议最终删除 pmsm_display_t，改为运行引擎发布小型、带周期号的一致状态快照。

### 7.2 LCD 当前显示的是固定示例值

User/moldue/display.c 的 display_foc 显示 24.12、31.27 和多组 0.00 等常数，没有读取 pm.display。main 只在初始化后调用一次。

这说明当前 LCD 不是在线状态观察链的一部分。后续应让 LCD 只读取低速状态快照，由后台任务按固定低频刷新，不得进入快环。

### 7.3 VOFA 绕过显示结构直读控制内部

User/moldue/vofa.c 的 vofa_start 直接读取 pm.adc.ia、ib、ic；大量被注释的候选信号也直接引用 pm.ctrl、pm.foc、pm.calibr、pm.idpm 和各 PID 内部字段。

当前问题：

- 调试工具必须知道整个 pm 的内部布局。
- 切换观测信号靠修改源码和注释，而不是稳定字段表或采集配置。
- 当前发送的是原始 ADC 计数，但没有单位和字段描述。
- vofa_send_data 的 num 参数没有写入帧，通道编号实际被丢弃。
- 帧没有周期号、时间戳、版本、有效性、字段表和丢包统计。
- send_buf 和 cnt 是无保护全局变量，没有边界检查。
- CDC_Transmit_FS 的返回值被忽略，无法处理 USBD_BUSY。
- USB 发送是异步的，当前代码提交后立即把 cnt 归零并复用同一缓冲区，没有明确的缓冲区所有权和发送完成协议。
- VOFA 调用当前被注释，因此还不是可验证的数据采集路径。

### 7.4 推荐的调试链路

    20 kHz 快环，唯一写者
      ├─ 发布 motor_status_snapshot_t
      │    用于状态、故障、模式和低速物理量
      └─ 写入固定容量 motor_trace_frame_t 环形缓冲区
           用于选定的高频控制信号

    低速诊断服务
      ├─ 读取一致快照
      ├─ 消费跟踪环形缓冲区
      ├─ 按字段标识、分频、触发条件和采样窗口组帧
      └─ 记录溢出、丢帧和传输忙统计

    传输适配器
      ├─ USB CDC
      ├─ UART
      ├─ FDCAN
      ├─ VOFA 编码器
      └─ 文件或主机回放格式

    消费端
      ├─ LCD
      ├─ VOFA
      ├─ 上位机记录
      └─ 离线回放与测试工具

关键规则：

- 显示和协议模块不能访问 motor_control_context_t 的私有成员。
- 状态快照和高频跟踪帧分开，避免把所有内部状态每周期复制一次。
- 快环不做浮点转字节、USB 调用或字符串格式化。
- 使用双缓冲、序号锁或极短临界区保证多字段一致性。
- USB 后端必须拥有提交中的缓冲区，直到发送完成或明确丢弃。
- 调试字段使用稳定字段标识和数据字典，记录名称、单位、类型、范围、采样率和版本。
- 调试器修改 PID 内存不能作为正式调参接口。参数应经过待提交配置、合法性检查和安全周期切换。

## 八、必须先于架构迁移处理的确定性问题

以下问题不是“重构偏好”，而是当前源码中可定位的安全或未定义行为。未关闭前不应进行带功率上电验证。

| 问题 | 证据 | 风险 |
|---|---|---|
| ADC 中断先于 pm 初始化启动 | Core/Src/main.c 第 117 至 126 行；User/motor/foc_ctrl.c 第 11 至 23 行 | 首个快环读取未初始化或半初始化状态 |
| 非法传感器选择可空指针解引用 | User/motor/pos_calc.c 第 38 至 53 行 | 冷启动可能 HardFault |
| 电流偏置累加器未初始化 | User/motor/foc_drv.c 第 623 至 645 行 | 偏置未定义，可能产生虚假电流 |
| 偏置阶段可能已经启动 PWM | foc_drv.c 初始化 ctrl_bit=start；foc_ctrl.c start 分支启 PWM | 校准不安全且污染采样 |
| 母线电压除法没有零值和有效性保护 | User/motor/foc_drv.c 第 570 至 574 行 | Inf 或 NaN 进入调制链 |
| 编码器读取使用未初始化数据 | User/motor/encoder.c 第 40 至 64 行 | 位置反馈不确定 |
| 编码器存在指针类型和返回值问题 | encoder.c 第 72 行及第 104 至 128 行 | C11 编译诊断和运行错误 |
| 观测器使用未初始化局部变量 | User/motor/eh_observer.c 第 36 至 43 行 | 输出不确定 |
| 软件故障检查在快环中被注释 | foc_ctrl.c 第 18 至 23 行 | 阈值存在但保护不生效 |
| TIM Break、Break2 禁用且 DeadTime 为 0 | Core/Src/tim.c 第 96 至 108 行 | CPU 或软件失控时缺少明确硬件关断链 |
| 状态转移没有正常闭环 | ctrl_bit 和 state_bit 分离，未发现正常进入 opera 的生产路径 | 依赖调试器改内存才能运行 |

处理原则：

- 先保证默认禁能、无效输入安全拒绝、非有限数安全停机。
- 先修未定义行为，再保存行为基线；不能把未定义行为当成需要兼容的“黄金输出”。
- 硬件 Break、Gate、死区和故障脚的最终方案必须结合原理图与实物验证，不能只凭软件推断。

## 十、推荐的渐进重构顺序

### 阶段 0：关闭确定性缺陷并冻结基线

目标：

- 让当前工程在默认禁能条件下可重复构建和冷启动。
- 修复未初始化、空指针、除零、错误指针和缺失返回值。
- 明确禁止带功率测试，直到安全链验收。

改动边界：

- 不调整 FOC 参数和控制律。
- 不做大面积改名和目录移动。
- 只处理确定性缺陷、初始化顺序和安全默认值。

验收：

- 冷启动不产生 PWM/Gate 允许。
- 非法配置、无效 ADC/编码器和零母线会确定性拒绝启动。
- 无 HardFault、Inf 和 NaN 进入 PWM 路径。
- 固件、ELF、HEX、MAP 和警告记录可重复生成。

### 阶段 1：先切开调试、显示和遥测

这是推荐的第一个架构改动。

目标：

- 引入小型状态快照和固定容量跟踪环形缓冲区。
- LCD、VOFA 和后续上位机只消费发布数据。
- 删除协议层对 pm 内部字段的直接依赖。

改动边界：

- pm 暂时保留为控制内部兼容对象。
- 不改变 PID、FOC、观测器的运算顺序和参数。
- 不在快环内调用 USB 或刷新屏幕。

验收：

- User/moldue 和 USB/通信协议代码不再直接引用 pm。
- 状态快照带周期号，读取不会出现跨周期混合。
- 跟踪缓冲区满时不阻塞快环，并记录明确丢帧计数。
- USB 忙时不复用正在发送的缓冲区。
- 同一输入下，控制输出与迁移前基线一致。

### 阶段 2：拆 common.h 和建立数据契约

目标：

- 建立基础类型、模块公开头、板级接口和运行数据契约。
- 分清原始采样、物理反馈、命令、请求和实际输出。

改动边界：

- 使用兼容适配器把旧 pm 字段映射为新数据对象。
- 每次只迁移一条调用链。

验收：

- 纯算法公开头可在主机编译器下独立包含。
- algorithms 不包含 main.h、bsp.h 或 HAL。
- 每个跨模块字段都有单位、方向、更新频率、有效条件和唯一写者。

### 阶段 3：建立运行引擎、板级端口和统一调度

目标：

- 让 ISR 只负责编排快周期。
- 建立明确的 20 kHz、1 kHz、100 Hz 和后台任务。
- 让板级层成为 ADC、PWM、Gate 和 Break 的唯一执行者。

验收：

- 快环最坏执行时间和抖动可测量。
- 通信和显示不会阻塞快环。
- 无效测量或超时命令会通过统一安全路径停机。
- 主机端可以用虚拟板级端口运行同一 engine_fast_step。

### 阶段 4：逐模块提取纯算法

迁移顺序：

1. 数学、PID 和滤波器。
2. Clarke、Park、反变换和 SVPWM。
3. 位置、速度和轨迹。
4. 观测器。
5. 标定、辨识和齿槽补偿。

统一接口形态：

    xxx_init(const xxx_config_t *config, xxx_state_t *state)
    xxx_reset(xxx_state_t *state)
    xxx_step(
        const xxx_config_t *config,
        const xxx_input_t *input,
        xxx_state_t *state,
        xxx_output_t *output)

验收：

- 算法无可写全局和函数静态历史状态。
- 两个实例互不污染。
- 相同初态和输入回放两次得到相同输出。
- 单元向量、边界、非有限数和饱和行为有测试。

### 阶段 5：参数辨识、自整定、离线回放与 HIL

目标：

- 将辨识和自整定做成受控实验会话。
- 统一记录原始输入、换算反馈、完整命令、请求、实际输出和版本。
- 复用生产算法完成离线回放、仿真和 HIL。

验收：

- 辨识失败、取消和超时不会部分修改活动参数。
- 候选参数可验证、拒绝、批准和回滚。
- 数据文件可以逐周期驱动生产算法。
- Elmo 工装未完成时，本平台仍可独立完成验证。

## 十一、不建议采用的做法

- 不要先全量重命名。物理语义没有确认时，机械替换会制造更可信但可能错误的名称。
- 不要把 pm 原样复制成另一个更大的新结构体。这只会转移耦合。
- 不要先大规模搬目录。依赖关系没有切开时，目录变化不会改善架构。
- 不要同时改变算法、参数、调度和接口。出现波形差异时将无法定位原因。
- 不要把所有内部字段都复制到一个 debug 结构体。应区分低频状态快照和按需高频跟踪。
- 不要依赖调试器直接改 volatile PID 字段作为正式调参方案。
- 不要在实时固件中引入动态内存、动态插件、复杂工厂或服务容器。
- 不要在安全缺陷未关闭前进行带功率上电验证。

## 十二、建议先建立的五张工程表

为了避免下一步凭字段名猜测，建议先建立以下中文可审查资产：

1. 变量词汇表：旧名称、真实含义、单位、坐标系、轴侧、范围、来源。
2. 数据所有权表：字段或对象的唯一写者、读者、更新时机、并发策略。
3. 模式与状态转移表：事件、前置条件、进入动作、退出动作、超时和安全去向。
4. 实时任务预算表：20 kHz、1 kHz、100 Hz 和后台任务的周期、最坏执行时间和优先级。
5. 调试字段字典：字段标识、名称、类型、单位、采样率、版本和有效性。

其中“变量词汇表”和“调试字段字典”最直接回应当前命名与 debug 耦合问题，也能为后续离线回放格式提供基础。

## 十三、建议下一步

建议下一步不要立即拆 pm，而是先执行两个小阶段：

1. 建立阶段 0 的安全、确定性和可构建基线，关闭明确的未定义行为。
2. 设计并实现“状态快照 + 高频跟踪环形缓冲区 + USB/VOFA 后端”的最小垂直切片。

第二步完成后，LCD、VOFA、上位机记录和后续离线回放将首次拥有稳定的数据边界；同时控制核心仍可保持旧 pm 布局，便于逐周期对比迁移前后波形。这是风险最低、验证价值最高的第一条架构切缝。
