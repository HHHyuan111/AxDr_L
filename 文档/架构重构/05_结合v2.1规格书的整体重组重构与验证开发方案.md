## 二、总体裁决

v2.1 规格书的核心方向是正确的，大部分原则可以纳入正式方案：

- App、Drive、Control、Target、Comm 分层；
- Target 独占 PWM、MOE、Gate 和硬件最终许可；
- 状态、控制模式、给定方式、起动策略、停车策略和角度来源分开；
- 原始采样、物理反馈、输出请求和实际采用结果分开；
- DriveState 唯一写入；
- 通信不访问 Drive 私有上下文；
- 固件、回放、C-SIL 和 HIL 复用同一套 Control/Drive C 源码；
- 分阶段构建、比较、验证和回退；
- Host 通过不能代替 ADC/PWM 时序、Break 和真实功率级验证。

但附件不能原样进入编码，必须先修订以下关键点：

1. 附件记录的 Git HEAD、origin 和分支状态不属于当前目录；当前工作区没有 Git 元数据。
2. 当前完整固件尚不能从空目录重复构建，不能把附件阶段 0 标为通过。
3. 目录中缺少 foundation、contracts 和 composition，容易让 drive_types.h 变成新的 common.h。
4. 单个 SPSC 队列不适合同时承载连续设定值、不可丢事件和紧急关断。
5. drive_fast_step 返回后 Target 才能应用输出，附件接口无法在同拍回交 Target 裁决并发布一致 Snapshot。
6. DriveState、StartPhase、活动故障和锁存故障不能全部集中给 drive_state.c 写入。
7. STOPPING 结束后，故障源仍活动时应进入 FAULT_ACTIVE，不能一律进入 FAULT_LATCHED。
8. Commissioning 只有总状态，缺少任务、阶段、授权、安全包络、取消、结果和候选参数合同。
9. “实际输出”必须区分算法请求、寄存器已提交和物理门极已观察三层事实。
10. 35 微秒 WCET 和 2.5 微秒抖动只能作为初始预算，必须由真实截止时间和测量结果冻结。

结论是：

> 采纳 v2.1 的原则和状态骨架，使用本文修订后的合同、所有权和验证门禁形成实施基线；不按附件原文机械落地。

### 4.2 为什么增加三个目录

foundation：

- 防止基础数值、时间、错误码散落；
- 不得包含电机巨型结构、HAL 或业务策略；
- 每个头文件职责单一，禁止再建立全项目伞形总头。

contracts：

- 放置 sample、feedback、command、event、actuation、snapshot 等跨层只读数据；
- 让 Target 和 Drive 共同依赖中立合同，避免 Target 反向依赖 Drive 私有类型；
- 只描述数据，不放算法状态和硬件寄存器。

composition：

- 负责静态分配上下文、绑定模块、初始化顺序、Fast/后台入口；
- production composition 是固件中唯一允许看见受限装配头的区域；
- 解决“Context 私有、禁止动态内存、调用者又需要静态分配”的矛盾。

验证侧允许一个不进入固件链接的受控例外：`verification/support/test_composition` 可以包含同一受限装配头并静态创建两个或多个实例，用于双实例、reset 和串扰测试。`source_guard` 分别维护 production/test 白名单，禁止普通 unit、workstation、comm 或 app 引用实例布局。这样不用公开 Context 字段、定长魔法 buffer 或动态内存，也能合法完成双实例门禁。

### 4.3 AxDr_App 的边界

AxDr_App 保留：

- STM32CubeMX 生成文件；
- CMSIS、HAL、中间件和 USB 设备代码；
- 启动文件、链接脚本、Keil 工程；
- 极少量 USER CODE 调用点。

AxDr_App 不再承载：

- FOC、PI、Observer 和轨迹公式；
- 电机状态机；
- 参数辨识策略；
- 遥测字段选择；
- 业务级 PWM/Gate 许可。

CubeMX 重新生成后必须执行差异检查。自定义 Target 逻辑放在独立源文件中，不写入可被生成器覆盖的非 USER CODE 区。

本项目采用“生成启动胶水白名单”，不要求重写 CubeMX 的非 USER `main`，但必须处理生成的 MSP 初始化会提前执行 `HAL_NVIC_EnableIRQ` 的事实。固定启动协议为：

1. `HAL_Init` 和系统时钟完成后，在 `USER CODE SysInit`、所有 `MX_*` 之前调用 `composition_pre_generated_init()`。它只建立最小 ISR-safe bootstrap 状态并保持全局可屏蔽中断关闭；不得访问尚未生成初始化的外设。板卡复位脚位和外部上下拉必须已由 G1 证明安全。
2. 生成的 `main.c` 按固定顺序直接调用 `MX_GPIO_Init`、`MX_DMA_Init`、`MX_ADC*_Init`、`MX_TIM*_Init` 等函数。它们内部即使设置 NVIC Enable，也因 bootstrap 屏蔽不能进入业务 ISR；NMI/HardFault 入口不得访问 Drive Context。
3. 在第一个 `USER CODE 2` 位置、任何 `HAL_ADC*Start*_IT`、Timer/PWM Start、通信接收和业务调用之前，调用一次 `composition_init_after_generated_peripherals()`。在仍屏蔽中断时，Target 绑定生成句柄、强制 Gate/MOE/CCR 安全态、清外设状态和 NVIC pending；composition 完成 Context、参数、命令缓冲和故障状态初始化。
4. 只有 Target 的显式 `target_start_sampling_and_irqs()` 按冻结顺序启动采样/Timer、开放所需 NVIC 并最终解除全局屏蔽。未列入白名单的 IRQ 保持关闭。

全局屏蔽区内禁止 `HAL_Delay` 或依赖中断完成的中间件初始化。若当前 `MX_USB_Device_Init` 或其他生成函数被证明确实依赖中断，必须通过 IOC/生成配置把其业务启动后移到 after-init，或采用单独 ADR 的 custom main；不能临时提前开全局中断。App、Drive、Comm 不得在运行期再次调用 `MX_*` 或直接启动/改写这些外设。CubeMX 再生成检查必须验证两个 USER 钩子、调用顺序和屏蔽区没有被破坏。

### 5.1 允许的依赖

    composition → target、app、drive、comm
    comm        → app 公共接口、contracts、foundation
    app         → drive 公共接口、config、contracts、foundation
    drive       → control、config 只读视图、contracts、foundation
    target      → contracts、foundation、板级私有配置、HAL/CMSIS 和生成的外设句柄
    control     → foundation
    verification/workstation → 各模块公开接口；仅 verification/support/test_composition 可使用受限装配头

### 5.2 禁止的依赖

- control 和 drive 不包含 main.h、HAL、BSP、USB、FDCAN、LCD 或 Simulink 头。
- drive 不读 ADC、不写 CCR/MOE/Gate、不调用 SPI。
- target 不执行 FOC、速度环、位置环、Observer 或实验策略。
- comm 不取得 drive_context_t 的地址。
- app 不写 PWM，也不直接修改 Fast 私有状态。
- Observer 不直接修改 id_ref、iq_ref 或 Duty。
- Simulink Wrapper 不复制控制公式。
- Legacy 和新实现不能同时写硬件输出。
- 禁止新的跨模块可写全局变量。

source_guard 对硬件写入分两类检查：

- 生成启动白名单：仅 CubeMX 生成 `main.c` 在 `composition_pre_generated_init()` 已建立中断屏蔽后，才可按固定序列调用指定 `MX_*_Init`；其后必须先进入 `composition_init_after_generated_peripherals()`/`target_start_sampling_and_irqs()`，运行期不得再次调用；
- 运行期写入白名单：只有 source/target 下的 actuation、fault_gate 和必要的板级 ISR 适配文件可以写 CCR、BDTR、MOE 和 Gate。

生成文件中的初始化写入不等于允许业务代码旁路 Target；白名单按符号和调用入口维护，不能按整个目录放行。

### 5.4 变量命名和调试边界

当前问题不是单纯“变量名不好”，而是一个对象同时扮演配置、输入、运行历史、输出、调试和通信协议，导致任何字段都可能被任意模块读写。重构时每个 Control 模块统一拆成：

- `*_config_t`：初始化后只读的物理参数和派生系数；
- `*_state_t`：模块私有历史，只能由本模块 `init/reset/step` 修改；
- `*_input_t`：本拍只读输入，必须含序号/有效性或由上层合同保证；
- `*_output_t`：本拍计算结果，不含硬件副作用；
- `*_diagnostics_t`：解释本拍结果的只读诊断值，不反向参与控制。

命名采用“物理含义 + 坐标/侧别 + 单位或语义”规则。例如 `phase_current_a`、`electrical_angle_rad`、`mechanical_speed_rad_s`、`dc_bus_voltage_v`、`fast_sequence`、`sample_age_ticks`；坐标量显式使用 `abc`、`alpha_beta`、`dq`，电机侧/负载侧和电角/机械角不得靠注释猜测。布尔量采用 `is_*`、`has_*`、`*_valid`、`*_requested`、`*_accepted` 等事实语义；禁止 `flag1`、`temp`、`data`、`value`、`mode2` 以及无定义的 `x/y/z` 跨越模块边界。

调试结构不再是全局“旁路总线”：

- 模块私有 diagnostics 可以由 step 产生，但只由 Snapshot/Trace 发布器挑选字段；LCD、VOFA、USB 不持有其地址；
- Trace 使用版本化 signal_id 和字段字典，不把 C 结构体布局或指针暴露为协议；
- `debug_mode` 不能选择 PWM 计算入口、覆盖引用值或跳过状态/故障/Target 许可；需要实验模式时，通过 App 的授权命令和 DriveState/Commissioning 合同表达；
- 调试器修改 PI 积分、Observer 历史、Duty 或故障位不属于受支持操作；参数调试走候选参数—校验—安全边界激活链；
- 诊断开关只能控制采样字段和分频，不能编译掉安全检查；Release 也保留最小故障快照和计数器；
- 防止 `drive_diagnostics_t` 演变成新的 `pm`：跨层快照只收录稳定、确有消费者的字段，模块详细诊断通过独立 Trace schema 版本扩展。

这样既降低调试耦合，也能保证关闭或增加某个观测字段不会改变控制结果。验证时要对“诊断全关/典型配置/最大配置”做 A/B 回放，并测量三种配置的数值一致性和 WCET 增量。

## 六、核心数据合同

### 6.1 周期和原始采样

cycle_stamp_t：

- fast_sequence；
- 单调时间；
- 采样触发身份；
- 采样相位或计数方向；
- 时钟域和时间单位。

sample_batch_t：

- ADC1、ADC2 原始注入值；
- 每个 ADC 的 JEOS/EOC、新鲜度和序号；
- 编码器原始帧、CRC/状态和年龄；
- Hall 原始状态；
- Break、Gate Fault、Driver Ready 等真实存在的板级事实；
- valid_mask 和采样错误原因。

保留原始层可以支持：

- 复核 ADC1/ADC2 同步；
- 重做标定换算；
- 单电阻重构；
- 离线回放板级换算；
- 追溯错误输入。

### 6.2 物理反馈

drive_feedback_t：

- 带单位后缀的相电流、母线、角度、速度和温度；
- 来源、方向、轴侧和坐标系；
- 周期号、有效掩码、新鲜度和质量；
- 当前反馈所对应的输出序号。

编码器速度若由差分和滤波得到，应放在可移植传感器处理或 Drive/Control 中，不默认塞进硬件 Target。

### 6.3 命令和事件

drive_command_t 表示最新、完整、可替换的运行意图：

- sequence；
- source；
- issued_at 和 deadline；
- run_request；
- drive_mode；
- reference_mode；
- 与模式匹配的判别联合体或严格有效掩码；
- 限制和“要求使用的已激活配置版本”；该字段只做一致性检查，不触发参数切换；
- 完整提交版本。

drive_event_t 表示不可按连续给定覆盖的离散事件：

- 故障确认请求；
- 校准开始或取消；
- Commissioning 开始或取消；
- 参数版本激活请求。

事件必须包含 source、event_sequence、issued_at、deadline、event_type、关联 command_sequence/config_version、判别式 payload 和协议版本。drive_mode 与 run_request 的唯一权威是最新完整 drive_command_t，不再通过事件重复表达。

正常停止通过最新命令中的 run_request=false 表达，不进入可能拥塞的事件队列。若需要独立的软件立即停止请求，应使用只能置位、由 Fast 清除的高优先级停止锁存；硬件 Break 仍走独立关断通道。

硬件 Break 和立即关断事实不经过普通命令队列。

### 6.4 输出的三层语义

actuation_request_t：

- Drive 生成的调制或 Duty 请求；
- 软件允许请求；
- 请求序号；
- 限幅状态；
- 可选采样计划。

actuation_commit_t：

- 原始 request_sequence；
- Target 接受、裁剪或拒绝结果；
- 实际写入及必要时读回的 CCR、BDTR/MOE 和 Gate 软件命令值；
- 寄存器提交成功状态，但不把软件 Gate 请求表述为物理桥臂已经启用；
- accepted_sequence 和计划生效的 Timer 区间；
- 当前是否仍仅为“已提交、尚未证明物理生效”；
- 拒绝、裁剪、最小脉宽、采样窗和硬件许可原因。

actuation_observation_t：

- 若板卡有门极、相电压或驱动器状态反馈，记录物理观察结果；
- 包含 observation_sequence、timestamp、valid_mask、来源和质量；
- 没有该能力时明确标为 UNSUPPORTED，不能用 CCR 或 MOE 读回冒充物理输出。

附件中的 AppliedActuation 建议拆成 commit 和 observation。Observer 使用哪个历史量，必须由 ADC/PWM 时序测量确认。

### 6.5 状态快照和跟踪

drive_snapshot_t：

- 同一发布序号的状态、模式、命令版本、参数版本；
- feedback 摘要；
- 角度来源和质量；
- 参考量和控制输出；
- actuation request、commit，以及板卡支持时的 observation；
- 活动故障、锁存故障和拒绝原因；
- Fast 执行时间和丢样计数。

trace_record_t：

- 固定长度；
- 由 Fast 单写者以 O(1) 写入环形缓冲；
- 支持字段配置、分频、触发和故障冻结；
- 缓冲区满时不阻塞，只计数丢帧。

Fast Trace Ring 只有后台 telemetry_dispatcher 一个破坏性消费者。dispatcher 再通过各后端独立的有界队列或缓存扇出到 LCD、VOFA、USB、FDCAN 和文件记录器；每个后端分别记录 busy、drop 和 high_water。禁止多个后端直接竞争同一个 SPSC 读指针。

LCD、VOFA、USB、FDCAN 和文件记录器只消费 Snapshot/Trace 或 dispatcher 输出，不读取 Drive/Control 私有字段。

## 七、Fast 运行闭环

### 7.1 修订后的两阶段接口

推荐周期编排：

    Cube/HAL ISR
      → composition_fast_step
      1. target_capture_cycle（sample + 当前可得 observation）
      2. target_convert_feedback
      3. drive_fast_prepare
      4. composition 组装 target_safety_input
      5. target_apply_request
      6. drive_fast_finalize
      7. publish_snapshot_and_trace
      8. schedule_next_encoder_transaction

建议接口形态：

    target_capture_cycle(
        target_context_t *target,
        cycle_stamp_t *cycle,
        sample_batch_t *sample,
        actuation_observation_t *latest_observation);

    drive_fast_prepare(
        drive_context_t *context,
        const drive_feedback_t *feedback,
        const actuation_history_view_t *matched_history,
        actuation_request_t *request);

    target_apply_request(
        target_context_t *target,
        const target_safety_input_t *safety_input,
        const actuation_request_t *request,
        actuation_commit_t *commit);

    drive_fast_finalize(
        drive_context_t *context,
        const actuation_commit_t *commit,
        const actuation_observation_t *latest_observation,
        drive_snapshot_t *snapshot);

这样可以同时满足：

- Drive 不调用 Target；
- Target 独占硬件写入；
- Drive 能看到 Target 是否接受请求；
- Snapshot 能包含同周期的提交结果；
- Snapshot 能带上当前最新的物理观察及其独立关联序号；
- Observer 可以使用按 feedback_corresponding_actuation_sequence 精确匹配的历史提交结果。

composition_fast_step 是完整周期的编排者；Target 只实现 capture、convert、apply 和板级 ISR 适配，不调用 Drive，从而保持 target 不反向依赖 drive。

`target_context_t` 私有保存生成外设句柄、不可变 capabilities、Break/Gate 粘滞事实和 Target 运行状态。`target_safety_input_t` 是 composition 在本拍冻结的显式输入，至少包含 cycle/request 序号、sample/feedback 有效性和新鲜度、母线物理值、Drive 功率许可、状态及参数/授权版本。Target 在 apply 瞬间还必须通过自己的句柄重新读取能实时取得的 Break、Gate Fault、Ready 和 Timer 状态；不能只相信较早快照，也不能从隐式全局 `pm` 获取安全条件。

`latest_observation` 在 capture 阶段取得，可能对应之前提交的输出，因此必须携带自己的 `observed_sequence` 和时间戳；它不能被强行标成刚产生的 commit。composition 把 observation 同时放入受限历史视图、finalize 输入和 Snapshot/Trace。没有物理观测能力时仍产生 `UNSUPPORTED` 记录，不省略数据流。

actuation_history_view_t 是固定容量、有界查找的历史视图。它必须按 feedback_corresponding_actuation_sequence 返回精确匹配项；未完成 G5 时序确认、找不到匹配项或 observation 失效时，依赖实际电压的 Observer 不得更新，并按策略拒绝输出或使用明确标识的安全降级路径。

drive_fast_prepare 不得提前永久提交所有输出相关状态。它只能推进与最终输出无关的测量状态，并把 PI 积分、抗饱和、实际电压历史等候选变化保存在 Context 的固定 pending 槽中。drive_fast_finalize 根据 Target 的接受、裁剪、拒绝或禁能结果提交或修正候选状态；Target 拒绝时不能保留按请求电压推进的积分器或 Observer 历史。

target_apply_request 在每次运行期寄存器写入前必须重新检查：

- Break 输入及粘滞锁存；
- Gate Fault、Driver Ready 和 Gate Enable 能力及当前状态；
- sample_batch/feedback 新鲜度和序号；
- 母线有效范围；
- 所有请求值有限；
- Duty 范围、最小高低脉宽和采样窗口；
- request_sequence 与当前周期匹配；
- Timer 配置、计数方向和装载窗口不变量；
- Drive 软件许可和 TargetCapabilities 支持。

任何检查失败时，故障或禁能永远优先于正常提交。具体寄存器顺序由每块板的安全真值表确定，原则上先阻止门极/MOE 继续输出，再处理 CCR 安全预装；不得为了更新 CCR 而暂时重新使能输出。异步 Break 与正常提交并发时，Break 必须获胜，commit 记录拒绝和实际读回状态。

### 7.2 生效序号

必须分别记录：

- request_sequence；
- accepted_sequence；
- scheduled_effective_sequence；
- observed_sequence；
- feedback_corresponding_actuation_sequence。

CCR 预装成功不等于 Duty 已经出现在引脚。未完成示波器测量前，不在算法中硬编码 k-1、半拍或一拍关系。

### 7.3 唯一触发和完整采样规则

- 由板级设计冻结唯一 Fast 主触发源和允许进入 composition_fast_step 的回调身份。
- 每个 sample_batch sequence 最多执行一次完整控制周期；重复、漏拍和乱序分别计数。
- ADC1、ADC2 的完成状态由 Target 聚合。ADC2 未完成或序号不匹配时，不阻塞等待、不读取旧 JDR，发布无效 sample_batch 并拒绝功率请求。
- 瞬态硬件故障由 Target 粘滞锁存首发时间、来源和寄存器状态，不能只在下一拍读取已经恢复的 GPIO 电平。
- 未通过该规则的批次仍可发布诊断，但不得进入正常控制输出。

### 7.4 Fast 内部顺序

    锁存完整命令和事件
      → 检查时限和输入有效性
      → Protection 前检查
      → DriveState 消费事件
      → 禁止态直接生成“硬件禁能请求”
      → Observer 使用已确认的历史输出
      → 起动和角度质量处理
      → 整数分频执行位置环、速度环和轨迹
      → 电流环和电压请求
      → 总电压限幅、反 Park、SVPWM
      → Protection 后检查，可撤销本拍许可
      → Target 最终裁决和提交
      → 回交结果并发布

### 7.5 快慢任务并发原则

初始版本建议让所有 Drive/Control 可变状态都由 Fast ISR 单一执行上下文更新：

- 20 kHz 电流环每拍运行；
- 1 kHz、100 Hz 任务由整数分频器在 Fast 内触发；
- 统计最坏情况时必须覆盖多个低速任务同拍运行的周期；
- 后台 main 只运行 App、协议、参数准备和遥测消费。

这样避免 drive_fast_step 与 drive_slow_step 并发写同一个 Context。

如果未来必须引入独立慢速中断，其与 Fast 之间只能通过邮箱、参数块和 Snapshot 交换，不共享可写字段。

### 7.6 Fast 禁止项

- 动态内存；
- Flash 擦写；
- LCD；
- 字符串格式化；
- USB/UART/FDCAN 发送；
- 无界循环；
- 未知 WCET 的轮询；
- 参数系数重算；
- 等待锁；
- 调试器直接修改内部控制历史状态。

### 7.7 无母线硬件资格授权

R4 的正常 Drive 输出许可保持硬禁能。为完成 G5/G7 中必须真实观察 PWM/PWMN、MOE、Gate、装载边沿和关断延迟的无母线测试，在 R5 离线门通过后提供独立的 `target_no_bus_qualification` 能力；它不是 `debug_mode`，也不授予 G8 带电资格。

该能力必须同时满足：

- 只存在于明确标识的 Qualification 构建，Release 构建静态关闭；
- 授权绑定 source_id、参数/配置版本、板卡序号、测试计划版本和短有效期；
- 测试前以接线检查和仪器读数证明直流母线物理隔离且低于预定安全阈值，结果写入证据包；
- 只允许白名单中的有限 PWM 频率、Duty、扇区、持续时间和切换序列，不接受正常速度/电流命令；
- Target 每次提交仍检查 Break、Gate Fault/Ready、Timer 不变量、母线和授权，超时、意外母线、通信丢失或任一故障立即失能；
- 测试序列由受控 qualification composition/App 计划驱动，最终寄存器写入仍只有 Target；
- token 不能被普通 App 命令、调试器变量或通信报文自行生成，不能复用于 G8；测试结束自动销毁并验证安全态。

这条路径只证明逻辑和无母线时序，不证明功率级、电流采样质量或带电关断。证据包的适用范围标为 `NO_BUS_QUALIFICATION`；门禁结论仍使用规定的五态，且不能据此生成任何“带功率已通过”结论。

## 八、状态、故障和 Commissioning

### 8.1 DriveState

建议保留 v2.1 的生命周期骨架，并按现行代码规范命名：

    DRIVE_STATE_BOOT
    DRIVE_STATE_SELF_TEST
    DRIVE_STATE_DISABLED
    DRIVE_STATE_CALIBRATING
    DRIVE_STATE_READY
    DRIVE_STATE_COMMISSIONING
    DRIVE_STATE_STARTING
    DRIVE_STATE_RUNNING
    DRIVE_STATE_STOPPING
    DRIVE_STATE_FAULT_ACTIVE
    DRIVE_STATE_FAULT_LATCHED

其他维度保持独立：

- drive_mode_t；
- reference_mode_t；
- start_strategy_t；
- start_phase_t；
- stop_strategy_t；
- stop_reason_t；
- angle_source_t；
- commissioning_task_t；
- commissioning_phase_t。

### 8.2 安全状态必须区分

“零输出”是含义过宽的词，必须拆成四个正交维度：

- power_permission_t：功率级禁止、允许请求、Target 接受或硬件钳制；
- output_strategy_t：正常调制、零电压矢量、滑行或主动制动；
- preload_state_t：CCR 未准备、已预装中性值或已预装下一请求；
- actuation_evidence_t：软件请求、寄存器已提交、物理已观察或无观察能力。

outputs_disabled 表示软件已经命令 MOE/Gate 禁能；zero_voltage_vector 表示功率级仍开关但线电压请求为零；coast 和 active_brake 是停车策略；preloaded_neutral_duty 只是输出禁能时的寄存器准备状态，不能混成一个枚举。

BOOT、SELF_TEST、DISABLED、CALIBRATING、READY、FAULT_ACTIVE 和 FAULT_LATCHED 必须请求 power_permission=disabled，而不是仅生成 50% Duty。没有 Gate 或相端反馈时，软件最多声称“禁能命令已提交”，不能声称物理桥臂已经关闭。

每个受支持板卡必须有安全真值表，覆盖 PWM/PWMN 电平或高阻、OSSR/OSSI、AOE、MOE、Gate 有效电平、CCR 初值、Break 锁存，以及冷启动、软件复位、看门狗、棕断和调试器暂停。真值表和实测结果共同决定 Target 的安全顺序。

### 8.3 故障模型

fault_manager 独立维护：

- fault_condition_active_mask：所有正在成立的 WARN、LIMIT 和 Trip 条件；
- trip_active_mask：要求退出或禁止功率运行的活动故障；
- fault_latched_mask：需要确认的历史故障；
- first_fault_context：首故障周期、状态、反馈和输出；
- fault_action：WARN、LIMIT、CONTROLLED_STOP、IMMEDIATE_OFF、POWER_CYCLE_LOCKOUT。

FaultAction 与生命周期的基本闭环：

| FaultAction | BOOT/SELF_TEST/CALIBRATING/READY/DISABLED | STARTING/RUNNING/COMMISSIONING | STOPPING | FAULT_ACTIVE | FAULT_LATCHED |
|---|---|---|---|---|---|
| WARN | 保持禁能或原状态并记录 | 保持状态并记录 | 继续停车并记录 | 保持禁能并追加上下文 | 保持禁能并追加上下文 |
| LIMIT | 保持禁能并记录，不因降额获得许可 | 应用预定义有界降额；不能保证安全时升级 | 应用更严格的停车包络；反馈/吸能条件失效时升级 | 保持禁能，只更新事实 | 保持禁能，只更新事实 |
| CONTROLLED_STOP | 保持禁能；trip 活动进入 FAULT_ACTIVE，已消失进入 FAULT_LATCHED | 仅在反馈、母线和吸能条件允许时进入 STOPPING，否则升级为 IMMEDIATE_OFF | 继续有界停车；新的更严重故障或超时立即升级 | 保持禁能和 FAULT_ACTIVE | 保持禁能和 FAULT_LATCHED |
| IMMEDIATE_OFF | apply 前撤销；按故障条件是否仍活动进入 FAULT_ACTIVE/FAULT_LATCHED | apply 前撤销；拍间由独立关断链处理；下一拍进入 FAULT_ACTIVE/FAULT_LATCHED | 立即终止受控停车并关断；下一拍进入 FAULT_ACTIVE/FAULT_LATCHED | 保持禁能，更新首故障/更高严重度 | 保持禁能；新活动 trip 转 FAULT_ACTIVE |
| POWER_CYCLE_LOCKOUT | 独立关断，置正交 lockout 锁存；活动时 FAULT_ACTIVE，否则 FAULT_LATCHED | 同左 | 立即关断并置 lockout | 保持 FAULT_ACTIVE 和 lockout | 保持 FAULT_LATCHED 和 lockout |

任何状态出现活动 trip 都不能进入 READY、STARTING 或 RUNNING。活动 trip 在非运行状态消失后转入 FAULT_LATCHED，等待确认。WARN/LIMIT 条件不应因为“仍活动”而把 DriveState 错误地改成 FAULT_ACTIVE。

`POWER_CYCLE_LOCKOUT` 不新增一个与生命周期并列的 DriveState，而是正交的 `power_cycle_lockout_latched`。它在故障源活动时配合 FAULT_ACTIVE，源消失后仍配合 FAULT_LATCHED；软件复位、看门狗复位和普通故障确认不得清除。每块 Target 必须定义如何证明“真实掉电并重新上电”，至少关联复位来源、直流母线低于安全阈值的持续时间及驱动器/外部锁存状态；无法可靠证明时，只允许受控维修流程清除。锁存实现不能依赖故障 ISR 中擦写 Flash，并必须经过 G4 的各类复位测试。

状态修正规则：

    故障触发 STOPPING，停车完成后：
      trip 仍活动  → DRIVE_STATE_FAULT_ACTIVE
      trip 已消失  → DRIVE_STATE_FAULT_LATCHED

故障确认接口只能发布请求。Fast 必须检查：

- 活动 trip 已消失；
- run_request 为 false；
- Target 返回的 `actuation_evidence_t` 达到该故障策略要求的关闭证据等级；
- 清除策略允许；
- `power_cycle_lockout_latched` 为 false；
- 旧命令不会自动恢复。

每种故障必须声明允许确认所需的最低证据：寄存器/MOE/Gate 命令已提交、独立 Break/驱动器锁存已成立，或物理 Gate/相端已观察。没有物理反馈的板卡最多声明“软件禁能已提交”；若某类故障要求物理关闭证据而 Target 不具备该 capability，确认保持 BLOCKED，不能用寄存器读回冒充物理关断。

“本拍撤销”只适用于 Target apply 前已经被软件检测到的故障。apply 后或两个 Fast 周期之间发生的故障，必须由已验证的 TIM Break 或等效独立硬件链在规定延迟内关断，Fast 下一拍再锁存状态。普通 GPIO/EXTI 只有实际接入关断链并通过延迟验收时，才能称为异步硬件关断；否则它只是需要 CPU 响应的故障事实。

### 8.4 Commissioning

COMMISSIONING 只表示“受控带电实验生命周期”，不能包含一个巨型辨识函数。完全不需要功率输出的零偏和静态传感器任务归入 CALIBRATING；需要桥臂激励的参数辨识、编码器电气偏置或齿槽任务归入 COMMISSIONING。准备和收尾阶段可以保持功率禁能，但任务分类不再含糊。

每个 commissioning_task_t 必须定义：

- 所需功率激励类型；
- 准备、预装、允许、激励、降能、完成、取消和失败阶段；
- 最大电流、电压、速度、时间、温度和位置范围；
- 授权来源和失效时间；
- 前置参数和反馈有效性；
- 取消和超时行为；
- 输出结果、置信度、残差和失败原因；
- 候选参数，不直接覆盖活动参数。

算法未收敛或用户取消不一定是 Drive 故障；只有安全条件失效、执行超时失控或硬件异常才进入 Fault。

建议任务合同：

    commissioning_request_start(task_id, authorization, envelope)
    commissioning_step(input, state, excitation_request, result)
    commissioning_request_cancel(task_id, reason)
    commissioning_result_get(task_id, candidate_parameters)

authorization 包含来源、权限、签发时间和截止时间；envelope 包含电流、电压、速度、位置、温度和持续时间上限。Drive 在 Fast 内执行 step，并把 excitation_request 合并到正常 actuation_request，再经过 Protection 和 Target，任务不得旁路 PWM 许可。App 负责计划、授权、取消、候选结果审批和持久化；Control 只负责纯计算。

## 九、命令和并发

### 9.1 三条通道

第一条：最新命令快照邮箱

- 用于连续设定、模式、限制和 run_request；
- latest-wins；
- 只读取完整版本；
- 旧版本可被覆盖，但记录覆盖计数；
- 过期后执行预定义停车策略。

第二条：有界事件队列

- 用于故障确认、参数切换、Commissioning、校准等边沿事件；
- FIFO；
- 不覆盖未消费槽位；
- 每拍消费数量固定上限；
- 满队列返回 BUSY 并记录；
- 正常停止来自 latest run_request=false，不经过该 FIFO；软件立即停止使用独立高优先级锁存，所以不会被旧事件堵塞。

第三条：硬件急停事实

- TIM Break 或经 G7 证明的等效硬连线保护可独立于 CPU 关闭硬件；普通 Gate Fault GPIO 只有实际接入该链时才具有相同资格；
- 不等待普通队列；
- Target 粘滞记录瞬态来源、时间和首发状态，Fast 下一拍锁存、分类和发布。

如果当前板卡没有合格的独立关断能力，G7、M2 及后续带电门禁必须标为 BLOCKED，不能用 NOT_APPLICABLE 绕过。

同一 Fast 周期的裁决顺序固定为：硬件 inhibit/Break 事实，其次软件立即停止锁存，其次最新 run_request=false，其次活动故障动作，其次离散事件，最后才是新的运行给定。事件按 event_sequence 去重，过期事件拒绝并记录；任何开始请求与同拍停止冲突时，停止获胜。

### 9.2 唯一生产者

USB、UART 和 FDCAN ISR 只把原始字节或帧放入各自 RX 缓冲。

后台 App：

    协议解析
      → 长度、版本、CRC、范围和状态校验
      → 多来源优先级与授权仲裁
      → 生成唯一完整命令或事件
      → 发布给 Fast

只有 App 的单一执行上下文是命令生产者，才能真实满足 SPSC。

### 9.3 并发实现

允许两种实现：

1. 在 Keil/ArmClang 与 ARM GCC 均验证的 C11 acquire/release 原子。
2. 由 Target 提供、测量过时长的极短临界区。

无论采用哪种方式，都必须：

- 检查生成汇编；
- 测试队列满、抢占、序号回绕和高频覆盖；
- 不把 volatile 当作同步；
- 不让 Fast 等待生产者；
- 对 Snapshot 读取设置固定重试上限，失败返回 BUSY 而非无界自旋。

## 十、可观测性和数据采集

### 10.1 第一条架构切缝

在大规模拆分 pm 前，先建立：

- 最小 drive_snapshot_t；
- 固定容量 trace_record_t 环形缓冲；
- 后台遥测服务；
- USB/VOFA 双缓冲或队列式发送后端；
- 明确缓冲区在途所有权和发送完成归还；
- busy、drop、high_water 和错误计数。

这一步不改变 FOC 公式和参数，却能：

- 解除 LCD、VOFA、USB 对 pm 的直接访问；
- 建立回放数据入口；
- 为重构前后比较提供周期一致证据；
- 捕获故障前后数据；
- 测量 Fast 时间和丢样。

### 10.2 数据格式

记录至少包含：

- 格式版本；
- source_id 和固件哈希；
- 板卡、电机、编码器身份；
- 参数和标定版本；
- 周期号和单调时间；
- 原始 sample；
- feedback；
- 完整命令；
- actuation request/commit，以及支持时的 observation、有效性、来源和关联序号；不支持时保存 UNSUPPORTED；
- 状态、角度来源和故障；
- 丢帧计数。

文件和通信协议显式定义端序、字段宽度、浮点格式、长度和 CRC。不能直接把 C 结构体内存当成长期文件格式。

## 十一、参数、配置和功能组合

### 11.1 参数生命周期

    参数输入
      → 解析和单位转换
      → 范围与一致性校验
      → 派生系数计算
      → 候选参数块
      → Host 回放或仿真检查
      → 在 DISABLED 安全边界请求切换
      → Fast 原子采用完整版本
      → Snapshot 记录活动版本
      → 保留上一版本用于回退

Flash 需要：

- schema_version；
- payload_length；
- CRC；
- 板卡/电机适用身份；
- 旧版本迁移函数；
- 掉电中断恢复策略；
- 双槽或其他可恢复提交方案。

参数格式变更必须服从“固件可回退、数据不可误解”的约束：

- 在新格式第一次写入前，先冻结旧格式定义、导出工具和一份可校验的设备参数备份；
- 新 schema 优先写入与旧格式不重叠的槽位；若必须复用区域，新固件必须先具备经过掉电测试的双向迁移或明确的一次性迁移/禁止回退协议；
- Boot 只接受身份、长度、版本和 CRC 同时匹配的完整记录，候选槽损坏时回到上一已确认槽，而不是恢复编译期随机默认值；
- 每个允许部署的回退固件都要在其能够识别的参数格式上重新通过安全启动；不能只证明镜像能够烧录；
- 在上述兼容合同和恢复演练通过前，重构固件不得向生产参数区写入新格式。

### 11.2 静态功能组合

初始固件只编入需要的算法：

- 单电机；
- 单一有感角度；
- 电流和速度模式；
- 一个受支持的 Observer 以后再加入；
- 不让所有 Observer、HFI、IPD、标定和大表同时常驻执行。

使用构建期静态选项，不使用动态插件、Factory、服务容器或动态内存。

## 十二、构建与版本控制方案

### 12.1 权威源

正式编码前必须决定：

1. 若真实 Git 仓库存在，优先从真实历史建立重构分支。
2. 若只有当前文件包，保持 AxDr原始代码 只读，在 Driver_lab/firmware 导入受控副本并初始化 Git。
3. 暂时不能使用 Git 时，以源集合哈希、补丁和证据包临时替代，但不作为长期方案。

建议基线标识：

- B0_RAW：未修改原始输入；
- B1_BUILDABLE：仅构建和 C11 兼容修复；
- B2_SAFE_BOOT_CANDIDATE：默认禁能和 P0 缺陷已经实现并通过离线测试，目标板资格可仍为 NOT_RUN；
- B3_CHARACTERIZED：在确定性缺陷修复后建立的 Golden Vector 和回放行为基线，并逐项记录相对 B0 的批准差异。

### 12.2 构建清单

- 删除 GLOB_RECURSE。
- 建立显式生产源文件清单。
- CMake、Keil 使用相同核心源集合。
- 增加脚本自动比较 CMake 清单与 uvprojx。
- Active 和 Release 配置中，新旧实现必须互斥；Shadow 配置允许两套算法同时编译和计算，但只有被选中的主实现能够把结果提交给 Target。
- 无论选择 Legacy 还是新 Control，都只能经过新 Target 输出。
- 每次空目录构建保存编译命令、ELF、HEX、MAP、尺寸、警告和哈希。

### 12.3 构建矩阵

| 构建 | 用途 |
|---|---|
| Host GCC Debug/Release | 单元、状态、回放、Sanitizer |
| Host Clang Debug/Release | 第二主机编译器和诊断 |
| ARM GCC Debug/Release | 目标固件和尺寸 |
| ArmClang/Keil Clean Build | 生产工程兼容 |
| Legacy baseline | 只用于行为表征 |
| Refactor shadow | 新算法计算但不拥有输出 |
| Refactor active | 通过门禁后由新算法请求输出 |

当前 Keil DFP 未就绪时必须标为 BLOCKED，不能用历史 AXF 冒充通过。ArmClang 逐文件语法检查不等于 Keil Clean Build；在该阻塞关闭前，可以建立 ARM GCC 临时开发基线，但不能取得“双工具链构建合格”或发布资格。

## 十三、分阶段实施方案

### R0：接收、权威源和不可变基线

目标：

- 解决无 Git 和来源身份问题。

工作：

- 固化原始源码、附件、历史产物和工具链哈希；
- 记录板卡、电机、编码器和未知项；
- 决定真实仓库或新受控工作副本；
- 建立需求编号和风险登记。

退出：

- 原始输入可重新验哈希；
- 工作副本有可回退身份；
- 未知、未执行、阻塞项明确。

不允许：

- 修改控制逻辑；
- 把附件 Commit 当成当前 HEAD。

### R1：恢复可重复构建和测试外壳

目标：

- 得到 B1_BUILDABLE。

工作：

- 修正 CMake 源清单；
- 统一 Keil/CMake 核心源；
- 固定工具版本和命令；
- 增加 Host C11、CTest 外壳；
- 单独处理 GCC/ArmClang 的 C11 编译缺陷。

退出：

- 两个独立空构建目录连续成功；
- ARM GCC 完整构建结果可追溯；ArmClang 语法检查单独记录，只有安装匹配 DFP 后的 Keil Clean Build 才能标为 ArmClang/Keil 构建通过；
- CMake/Keil 源集合差异自动报告；
- 核心警告不退化。

若 Keil DFP 仍缺失，R1 可以形成“ARM GCC 临时开发基线”并继续纯 Host/离线工作，但双工具链门保持 BLOCKED，禁止阶段发布和目标板部署资格。

回退：

- 只回退构建专用提交，不覆盖历史产物。

### R2：安全启动和确定性缺陷遏制

目标：

- 得到 B2_SAFE_BOOT_CANDIDATE，但仍禁止功率验证。

工作：

- 默认 PWM/Gate 禁能；
- 完成 Context、配置和传感器初始化后才开放采样；
- 修复零偏累加、空指针、除零、错误指针、缺失返回和未初始化局部变量；
- 检查 ADC 回调来源；
- 建立统一紧急关闭入口；
- 非有限数、无效反馈和非法枚举全部安全拒绝。

离线退出：

- Host 缺陷测试通过；
- 所有修复单独记录，不重新整定。

目标板资格项：

- 无母线冷启动无 HardFault、NaN 和 PWM 许可；
- 校准期间 Gate 始终关闭；
- 该项没有设备时标为 NOT_RUN，不阻塞 R2.5 至 R6 的离线工作，但持续阻断任何带电门禁。

回退：

- 源码可回看 B1；设备只允许使用通过相应安全门的固件。每次回退都要重新构建并执行安全启动回归，不能只验证源码能切换。

### R2.5：修正后 Legacy 行为表征

目标：

- 得到 B3_CHARACTERIZED，为 R3 和 R6 提供可信比较基线。

工作：

- 逐项登记 B0 中未定义行为及 R2 修复后的预期差异；
- 为 Clarke、Park、PI、SVPWM、速度差分等建立 Golden Vector；
- 建立 Legacy Host 表征入口和版本化输入/输出格式；
- 保存参数、单位、采样周期、编译器、优化和数据 SHA-256；
- 有硬件记录时只纳入来源可追溯的数据，没有硬件时相应场景标为 NOT_RUN。

退出：

- 不把未初始化值、空指针、NaN 或其他未定义行为固化为 Golden；
- R2 批准修复与 B0 差异逐项可解释；
- R3 的“Legacy 行为未变”和 R6 的 Shadow 比较拥有预先登记的判定依据。

回退：

- 删除或停用表征外壳不会改变 B2 生产行为；数据集按版本保留，不覆盖旧数据。

### R3：数据合同和可观测性垂直切片

目标：

- 在保留 Legacy 控制的情况下建立稳定数据边界。

工作：

- 增加 cycle、sample、feedback、command、actuation 和 snapshot 合同；
- 建立最小 Trace Ring；
- LCD、VOFA、USB 改为消费 Snapshot/Trace；
- 修复 USB 在途缓冲区所有权和 BUSY 处理；
- 建立第一份版本化回放记录。

退出：

- comm、display、VOFA 不再直接引用 pm；
- Snapshot 多字段属于同一发布序号；
- Trace 满时不阻塞 Fast；
- 可把同一记录送入 Host 回放外壳；
- Legacy 输出行为没有未经解释的变化。

回退：

- 关闭新遥测消费者，不撤销安全启动修复。

### R4：Target 采集、输出许可和回执

目标：

- 建立唯一硬件所有权。

工作：

- ADC 原始采集和板级换算进入 Target；
- 所有 CCR、MOE、Gate 写入进入 target_actuation；
- 实现 request、commit、capability 和拒绝原因；
- Legacy FOC 通过单向包装只返回请求，不再写寄存器；
- 建立 Fake Target 供 Host 使用；
- 本阶段所有真实输出许可强制为 false：允许在 Shadow 或无功率条件下核对请求、拒绝原因和寄存器装载路径，但 Target 不接受带功率使能令牌。

退出：

- 静态扫描和链接清单证明只有 Target 写硬件；
- 禁止态和无效输入不能使能输出；
- Host 可替换 Target；
- 新旧 FOC 不可能同时写 PWM；
- 无功率验证 Target 的真实寄存器状态；
- 即使 Legacy 和新 Control 同时参加 Shadow 计算，也只有选定主实现能够提交请求，且该请求仍被本阶段的硬禁能策略拒绝。

R4 不能取得首次上电资格。R5 离线门通过后，才可使用 7.7 的专用无母线资格授权去关闭 G5/G7 所需的逻辑输出与关断测试；该授权不能启动正常 Control，也不能转化为 G8 许可。只有聚合 G0～G7 全部 PASS 后，才允许按 G8 流程首次使能功率输出。

回退：

- 可以选择 Legacy Control，但必须继续经过新 Target。

### R5：状态、命令、故障和 Commissioning 骨架

目标：

- 建立可穷举的运行内核。

工作：

- 实现 latest-wins 命令邮箱、有界事件队列和硬件急停通道；
- 实现 DriveState 唯一写入和事件优先级；
- 实现 fault_manager、FaultAction 和确认请求；
- 实现 READY、STARTING、STOPPING 的进入、周期、退出和超时；
- Commissioning 先只实现生命周期、资源占用和拒绝骨架；不实现带功率任务，未支持任务返回 UNSUPPORTED；
- 实现 7.7 的无母线资格授权合同和自动失效逻辑，但只在 Qualification 构建中可用；
- 发布同序号 Snapshot。

退出：

- 状态×事件全部有确定结果；
- 禁止态永远没有软件 PWM 许可；
- 在本次 apply 前检测到的严重故障必须在同拍拒绝请求；发生在两次 apply 之间的异步故障由已验证的硬件关断链立即失能，下一次 Fast 再锁存、分类并发布；
- 故障不能自动恢复旧命令；
- 队列满、回绕、抢占和超时测试通过；
- Commissioning 未实现任务返回 UNSUPPORTED 并保持安全。

回退：

- 回到 R4 的安全禁能或 Legacy 请求，不恢复旧状态机作为设备运行路径。

### R6：基础 Control 纯算法迁移

目标：

- 提取数学、PI、FOC 和 SVPWM。

顺序：

1. 基础数学和限幅。
2. Clarke、Park 和反 Park。
3. PI 配置、状态和诊断拆分。
4. SVPWM 和 Duty 请求。
5. 电流环完整管线。

每个模块：

- config/state/input/output 分开；
- init/reset/step；
- 不访问 pm、HAL 或寄存器；
- 两实例无串扰；
- 先 Shadow 对比，再切换 Active。

退出：

- Golden Vector 和逐拍回放通过；
- 差异在预先登记的容差内；
- NaN、Inf、饱和和边界行为明确；
- Host 与 ARM 使用同一源文件。

回退：

- 每个模块只允许在预先登记的 Shadow 对比失败时切回 Legacy 主实现；回退不绕过新 Target、状态许可和故障链；
- Active 切换点、参数版本和数据集版本必须写入证据包，避免把算法回退误判成整定变化。

### R7：有感最小可证明闭环

目标：

- 得到有感最小闭环候选，证明新的运行链能安全、确定地驱动一个受控对象；这还不是核心架构清理完成。

范围：

- 单一确认过的编码器；
- 电流模式；
- 速度模式；
- 位置模式在前两者稳定后加入；
- 统一整数分频调度；
- 编码器 DMA 或可接受的 WCET 证据；
- 命令超时、传感器失效和正常停机。

退出顺序：

- Host 回放；
- 目标板无母线；
- PWM/ADC 时序；
- Break/Gate 关断；
- 低压限流空载；
- 小电流；
- 低速；
- 正反转和停车；
- 带载边界。

只有真实完成的层级才能标为通过。

回退：

- 带电测试只允许回到最后一个通过同等或更高安全门的固件和参数组合；
- 回退后必须重做安全启动、参数兼容和关断自检，不能复用上一镜像的通过结论。

### R8：核心清理和架构发布候选

工作：

- 删除全局 pm；
- 删除 common.h 总头和重复 FOC 入口；
- 删除 Legacy Wrapper；
- 把尚未迁移的 Observer、HFI、IPD、单电阻等高级算法从生产清单移入只读 reference/legacy_archive；它们保留来源身份，但不参与核心固件编译；
- 完成参数格式兼容、备份、迁移、掉电恢复和固件回退验证；
- 完成许可证、资源、构建和发布报告；
- 校验 CubeMX 再生成；
- 形成长期维护门禁。

退出：

- 没有未解释的可写全局算法状态；
- control/drive 无 HAL；
- 只有 Target 写硬件；
- Active/Release 中新旧源不会同时编入；Shadow 中只有一个请求提交者；
- 文档、代码、测试和证据一致。

R8 才是“核心架构重构完成”的推荐边界。它要求有感最小闭环证据仍有效，同时把过渡性全局状态、总头和 Legacy 包装真正移出生产路径。

### R9：算法复现平台与高级功能工作包

R8 后按独立工作包逐项增加：

- 单一基础 Observer 和 PLL；
- I/F 起动、融合和失锁；
- 参数辨识会话；
- 自整定候选参数；
- 标定和齿槽补偿；
- C-SIL、Simulink Wrapper 和 HIL；
- 单电阻采样计划和重构；
- HFI、IPD、弱磁和 MTPA。

每个工作包必须：

- 只有一个算法或一种硬件能力；
- 有独立 Context、数据合同、参数 schema、Golden/Replay 数据集、功能开关、资源预算和风险登记；
- 不改变基础 FOC 和 Target 接口，确需改变时先形成 ADR 并重跑受影响门禁；
- 从 Shadow、离线、无功率、低压限流逐级取得资格；
- 未验证时不进入 Release 组合，也不阻塞其他已合格工作包发布。

R9 不是一个“一次性全部通过”的阶段。无感、辨识、自整定、HIL 等分别拥有版本、门禁和完成状态。Elmo 只在 workstation/benchmark 中作为未来设备适配器，不成为固件或核心算法依赖。

### 资源预算冻结点

资源和实时指标不能在测试失败后随意放宽，采用三次冻结：

1. R1 保存 P0 基线：Flash、RAM、各段尺寸、主栈/中断栈估计、20 kHz Fast 的现有观察值和构建选项。
2. R4/R5 冻结候选预算：Fast/Slow/通信各自 CPU 配额，Context、Trace、队列、栈和通信带宽上限；没有实测的值明确标成“假设”。
3. G5 时序确定后、G6 压力测试前冻结发布预算：从样本可用到 CCR 生效的真实截止时间、允许抖动、最大临界区、最大通信 ISR 占用、栈水位余量、RAM/Flash/Trace 余量。

冻结后的预算变化必须有 ADR、测量依据和受影响门禁重跑记录；禁止为了让测试变绿而只修改阈值。高级算法工作包要在合入前声明自己的增量预算，超过余量时必须通过功能组合裁剪解决。

## 十四、科学验证方法

### 14.1 需求追踪

为关键条款建立稳定编号：

- ARCH：分层和依赖；
- DATA：数据合同和所有权；
- STATE：状态与转移；
- SAFE：安全和故障；
- RT：实时性；
- CTRL：控制算法；
- DIAG：诊断、Trace 和回放；
- BUILD：构建和工具链；
- MIG：迁移和回退。

每个条款必须能追踪到：

    条款
      → 架构决策记录
      → 实现文件和接口
      → 测试用例
      → 运行结果
      → 证据制品和哈希

### 14.2 数值验证

不同目标采用不同判定：

- 状态、枚举、错误码、许可和故障位：精确相等。
- 同编译器未改公式的迁移：优先逐位或严格浮点比较。
- 跨编译器数学：预先定义绝对误差、相对误差和必要的 ULP 上限。
- 饱和和扇区边界：单独定义左右边界预期，不能用宽容差掩盖分支差异。
- NaN、Inf、除零：必须返回明确安全结果。
- 物理闭环：按带宽、稳态误差、超调、建立时间、电流峰值和温升评价。

Golden Vector 必须记录：

- 来源实现和 source_id；
- 输入单位、采样周期和方向；
- 参数版本；
- 编译器和优化；
- 期望输出；
- 容差依据；
- 数据文件 SHA-256。

### 14.3 属性和不变量

除固定向量外，增加属性测试：

- Clarke/Park 正反变换一致性；
- 角度加减 2π 不改变物理结果；
- 电流、电压和 Duty 始终有限；
- Duty 在合法范围；
- 禁止态许可永远为 false；
- 无效反馈不能进入 PWM 写入；
- 两个 Context 互不影响；
- reset 后同输入得到相同输出；
- 命令序号回绕比较正确；
- Snapshot 不混合不同周期。

覆盖率只作为发现遗漏的指标，不作为正确性证明。状态转移、故障动作和所有安全 Guard 的真假分支必须全部被测试。

## 十五、验证门禁

每个门禁先建立“证据合同”，至少包含：责任人、source_id/固件哈希、板卡和原理图/BOM 版本、仪器及校准状态、接线与工况、明确阈值、原始数据位置、分析脚本哈希、结论和批准人。阈值必须在运行前冻结，结果失败后不得通过改阈值追认。

所有门禁只使用 PASS、FAIL、BLOCKED、NOT_RUN、NOT_APPLICABLE 五种状态。安全关键能力未知、图纸或板号无法绑定、没有适用仪器或缺少独立关断链时必须标为 BLOCKED，不能用 NOT_APPLICABLE 隐藏。高一级门禁不得覆盖低一级的 FAIL/BLOCKED/NOT_RUN。

G0、G2、G3 是聚合门，使用以下稳定子门消除“部分通过”歧义：

| 聚合门 | 稳定子门 |
|---|---|
| G0 | G0.SOURCE 来源身份；G0.HOST 主机构建；G0.ARM_GCC 完整目标构建；G0.KEIL 真正 Clean Build |
| G2 | G2.DATA 数据唯一写者；G2.HW 硬件唯一写者；G2.STATE 生命周期唯一写者；G2.DEP 依赖方向；G2.GLOBAL 全局状态；G2.BUILD 源清单和 Shadow 单提交者 |
| G3 | G3.SAFETY 安全拒绝；G3.LEGACY 修正后行为表征；G3.CONTRACT 数据合同；G3.TARGET Fake/拒绝；G3.STATE 状态×事件/故障；G3.CONTROL 纯算法/双实例；G3.REPLAY 记录回放和 Sanitizer |

每个子门独立使用五态和独立证据。只有声明范围内所有适用子门均为 PASS，聚合门才是 PASS；任一 FAIL 则聚合 FAIL，任一 BLOCKED 则聚合 BLOCKED，其余未执行项使聚合门保持 NOT_RUN。阶段矩阵可以要求某个子门通过，但在其他子门未完成前不得把整个 G0/G2/G3 标为 PASS。首次功率运行所要求的 G0～G7 PASS 指聚合状态全部 PASS。

### G0：来源和构建

- source_id、工具链、源文件清单和产物哈希完整；
- 空目录重复构建；
- PASS、FAIL、BLOCKED、NOT_RUN、NOT_APPLICABLE 明确区分。

### G1：板卡能力

先把测试对象绑定到板卡版本、原理图和 BOM 哈希、栅极驱动器型号/版本、电压域和连接器针脚，再建立 TargetCapabilities 表：

- PWM/PWMN；
- ADC 通道和触发；
- BKIN/BKIN2；
- Gate Enable；
- Gate Fault；
- Driver Ready；
- 母线、相电压和温度；
- 编码器；
- 预充、接触器和制动电阻。

每项同时记录方向、有效电平、上拉/下拉和复位默认状态、MCU 复用、隔离/电平转换、滤波、锁存、软件可见性和失电状态。PWM 还必须明确互补输出、死区由 MCU 还是驱动器负责、最小脉宽和采样拓扑。每项标记已接线、硬连线不可读、未实现或待测量；禁止实现不存在的“幽灵信号”。任一安全关键字段未知时，带电门保持 BLOCKED。

### G2：静态所有权

- 只有 Target 写 CCR、BDTR、MOE 和 Gate；
- control/drive 不含 HAL；
- DriveState 只有一个写者；
- 无新可写全局算法状态；
- CMake 无 GLOB_RECURSE；
- Active/Release 中新旧实现互斥；Shadow 可同时计算，但链接/静态扫描必须证明只有选定主实现能够提交 request，且只有 Target 能提交硬件。

### G3：Host 单元与集成

- 数学、PI、SVPWM；
- Context 双实例；
- 命令、事件和参数切换；
- 状态×事件穷举；
- 故障动作和确认；
- Snapshot 一致性；
- Target 拒绝原因；
- Replay 和 Sanitizer。

### G4：目标板无母线

- 冷启动、软件复位、看门狗复位、棕断恢复和调试器复位各自执行安全启动序列；
- 证明 `composition_pre_generated_init` 在所有生成 NVIC Enable 之前生效，屏蔽区内没有 `HAL_Delay`/中断依赖等待，after-init 清除了外设与 NVIC pending，并且只有 `target_start_sampling_and_irqs` 最终开放中断；
- 在 Context/参数/传感器/状态完成前人为制造早到 ADC、DMA、Timer 和通信中断，证明不会读取未初始化状态或取得输出许可；
- ADC 回调来源；
- ADC1/ADC2 完成和新鲜度；
- Fast GPIO 周期；
- 编码器事务；
- 所有禁止态下 MOE/Gate 关闭；
- Break/Fault 状态记录；
- 栈高水位；
- 每种复位来源的 Gate、MOE、CCR 和故障锁存初态都有寄存器快照和引脚证据。

### G5：PWM/ADC 时序

涉及真实 PWM/MOE/Gate 翻转但尚未带功率的项目，只能在 R5 离线门通过后使用 7.7 的无母线 Qualification 构建和限时授权；普通调试变量、Release 固件或正常运行命令不能代替该合同。

示波器或逻辑分析仪同时观察：

- PWM/PWMN；
- ADC 触发代理；
- Fast 入口和出口；
- Gate/MOE；
- Break/Fault。

确认：

- ADC 采样窗口；
- ADC2 读取时已经完成；
- CCR 装载边沿；
- 反馈和输出序号关系；
- MCU 实际死区、驱动器传播延迟、最小高/低脉宽、模拟前端建立时间和 ADC 真正采样孔径满足板级预算；
- 在最小/最大 Duty、扇区边界和母线变化下仍有合法采样窗口，窗口不足时请求被拒绝或使用已验证的重构策略；
- 第一次使能无旧 CCR 窄脉冲；
- 停机末脉冲正确。

### G6：实时预算

20 kHz 周期为 50 微秒。35 微秒 WCET 和 2.5 微秒抖动作为初始工程警戒线，不作为未测量的最终指标。

测量要求：

- DWT 周期计数与 GPIO 双证据；
- 覆盖低速任务同拍、Observer、诊断和通信中断压力；
- 固化 NVIC 优先级表，测量最大关中断/临界区，给通信 ISR 设置可验证的单次和周期占用上限；
- 报告观察最大值、分布、持续周期和优化等级；
- 有限测量得到的是 observed maximum，不冒充数学上已证明的绝对 WCET；
- 最终预算由采样完成到目标 CCR 生效边沿的真实截止时间反推；
- 对 Fast 丢拍、重复调用、样本过期、CCR 截止时间错过和队列积压分别定义计数、锁存和安全动作，压力测试必须证明动作确实发生。

### G7：硬件关断

首次进入 G8 前，G7 只按“逻辑电源开启、直流母线物理隔离”的范围验收独立关断链、门极信号和最坏软件冻结情形，并用与 G5 相同的资格授权。带功率后的关断确认作为 G8 最早的受限步骤另行保存；它不是首次进入 G8 的循环前置条件，但一旦失败必须立即撤销 G8 资格。两个范围的结果不得互相代替。

- Break 来源、极性、滤波和锁存；
- BKIN/BKIN2；
- OSSR、OSSI、AOE、MOE；
- Gate 有效电平和驱动器真值表；
- 软件冻结、关中断和调试器暂停；
- 对 Break、Gate Fault、驱动器 Ready 丢失等每条物理路径分别规定最大允许延迟，并在多个 Duty/扇区下测量故障输入到门极关闭和相端失能的延迟；
- 棕断、看门狗和复位后的安全状态。

只有真实连到 Timer Break/驱动器关断等异步硬链的信号才可声称“与软件无关”。普通 GPIO Gate Fault 若只是由 Fast 轮询，属于同步软件保护。若板卡没有足以覆盖软件冻结和调试暂停的独立关断链，G7 为 BLOCKED，禁止进入带电 G8。测试只采用厂商/板卡允许的故障注入端和安全测试夹具。

### G8：低压限流

G8 的前置条件是同一 source_id、参数版本和板卡对象的 G0～G7 全部 PASS。任何 BLOCKED、NOT_RUN 或过期证据都不允许用“低电压风险较小”绕过。

顺序：

1. 逻辑电源，功率关闭。
2. 低母线，电源限流，空载。
3. 不旋转的有限脉冲下确认 Break/Gate 关断并与 G7 无母线结果关联；失败立即退出 G8。
4. 小电流模式。
5. 低速模式。
6. 正反转、加减速和停车。
7. 编码器失效和命令超时。
8. 逐步增加电压、负载和速度。

每步提前定义电流、速度、时间、温度和占空比上限。

### G9：加载和故障覆盖

只有对应工况的 G8 已通过，才允许执行 G9。每种故障要先从 FaultAction×DriveState 表派生最大检测/关断/锁存/恢复时限和是否允许重启，再选择不会制造额外危险的注入方法；禁止通过短接相线、绕过限流或破坏保护器件来“验证”故障处理。

覆盖：

- Break 和 Gate Fault；
- 软件过流；
- 母线过压、欠压；
- ADC 冻结、失配和无效；
- 编码器超时；
- Observer 失锁；
- 命令超时；
- 堵转；
- 起动和飞车捕获失败；
- 停车超时；
- Fast 超时和 Timer 更新错过；
- 高通信中断负载。

每项保存输入条件、状态序列、输出请求、提交结果、物理波形、故障位、恢复条件和是否允许重启。

| 生产 C/构建清单合入 | source_guard、Host 全矩阵、ARM GCC Debug/Release | 无 | Keil 可暂时 BLOCKED，但必须显式显示 | 可继续离线开发，不可打正式阶段/发布标签 |
| R2～R6 离线候选 | 上述全部、Golden/Replay/Sanitizer、阶段适用 G2/G3 | 无 | G4～G9 可 NOT_RUN；Keil 可 BLOCKED | 名称必须带“离线候选”，不能宣称板卡或发布合格 |
| target_no_power 资格 | 与待测镜像完全相同的 source_id 和构建证据 | G1、G4 及阶段适用项 | 功率项 G5～G9 可 NOT_RUN | 只允许无母线验证 |
| 首次 target_powered | 固件、参数和脚本哈希已冻结 | G0～G7 全部 PASS，人工批准 G8 工况 | 不允许 BLOCKED/NOT_RUN | 只在批准的电压、电流、速度、时间和负载包络内运行 |
| R8 核心发布 | 双工具链 Clean Build、全 Host/ARM 回归、资源报告 | 所有适用 G0～G9 PASS | 仅真正无关项可带理由 N/A | 核心架构发布合格 |
| R9 功能发布 | 基于 R8，新增功能的全自动回归和增量预算 | 受影响门禁重新 PASS | 未发布的其他工作包可 NOT_RUN | 只发布该功能声明的能力范围 |

所有阶段标签和发布证据至少在对应固件的整个支持期内保持可取回：清单、哈希、构建日志、ELF/HEX/MAP、测试报告、原始波形/Trace、分析脚本、参数和批准记录必须能由标签反查。普通 CI 日志按项目保留策略存储，但任何安全 FAIL、批准偏差及其关闭证据不得只留在易过期的 CI 页面中。

## 十七、迁移纪律和回退

### 17.1 一次只改变一个变量

同一个提交不同时进行：

- 大范围移动；
- 控制公式修改；
- 参数整定；
- 硬件保护启用；
- Observer 更换；
- 通信协议修改。

纯移动提交和行为修改提交分开。

### 17.2 Legacy 包装纪律

- 只允许新框架调用 Legacy；
- Legacy 不反向调用新框架；
- Legacy 只返回请求，不写硬件；
- 每迁完一个模块删除对应旧入口；
- Shadow 比较通过后才 Active；
- 运行时不保留两个硬件写者。

### 17.3 双回退概念

源码回退：

- 可以查看或比较 B0_RAW；
- 每阶段有标签、提交和补丁。

设备部署回退：

- 只能回退到最后一个通过相应安全和硬件门禁的固件；
- 不能因为旧固件“以前能转”就重新部署未通过安全门的版本。

## 十九、里程碑和完成定义

### M1：离线架构开发候选

- Host 与 ARM GCC 构建通过，ArmClang/Keil Clean Build 的真实状态单独列出；
- 数据合同、状态、命令、故障和 Target Fake 通过；
- Control/Drive 无 HAL；
- 状态和输出所有权扫描通过；
- 无功率硬件项目可以仍为 NOT_RUN，但必须显式展示。

若 Keil DFP 仍为 BLOCKED，M1 只能称为“离线开发候选”，不是正式阶段合格或发布资格。

### M2：板卡资格合格

- ADC/PWM 时序已测；
- Break/Gate 能力已确认；
- 禁止态真实关断；
- Fast 时间满足冻结预算；
- 首脉冲、停机和故障波形合格。

### M3：有感最小闭环合格

- 电流和速度模式通过低压、空载和带载；
- 编码器失效、命令超时和停车结果确定；
- 回放可重现关键状态和输出。

这是“新运行链已在最小闭环中得到证明”的边界，不代表过渡性 pm、common.h 和 Legacy 已清理。

### M4：核心架构重构合格

- R8 清理完成，生产构建不再包含 pm、common.h 总头、重复入口和 Legacy Wrapper；
- 双工具链 Clean Build、参数迁移/固件回退、资源预算和所有适用门禁通过；
- M2/M3 的板卡、安全和最小闭环证据与发布 source_id 一致；
- 文档、代码、测试、构建清单和证据包相互可追踪。

这是当前“架构重构与基础验证完成”的推荐边界。

### M5：算法复现平台合格

- Trace、数据格式、离线回放、C-SIL 和 HIL 接口稳定；
- 参数候选、审批和回退可用；
- 算法能用同一生产 C 源码做 A/B 比较。

### M6：具体高级功能合格

无感、HFI、单电阻、弱磁、MTPA、参数辨识、自整定分别拥有独立验收，不与 M3 混成一个总开关。

不得只用“v2.1 重构完成”一个状态隐藏各里程碑差异；M1～M6 分别报告，后一里程碑不能把前一里程碑的 BLOCKED/NOT_RUN 自动变成 PASS。

## 二十二、外部一手资料交叉验证

厂商框架支持以下通用原则，但不能替代 AxDr 实测：

- ST MCSDK 把 START、SWITCH_OVER、RUN、STOP 以及活动故障、故障消失待确认分成独立状态，并说明应用不应直接修改状态机。

- TI Universal FOC 将应用、HAL 和底层驱动分层，硬件动作通过 HAL。

## 二十三、最终建议

最优路线不是立即重写 FOC，也不是先把目录整理漂亮，而是：

    建立可追溯源和可重复构建（缺失工具链显式 BLOCKED）
      → 关闭确定性和启动安全缺陷
      → 先切开 Snapshot/Trace/通信
      → 建立 Target 唯一硬件所有权
      → 建立状态、命令和故障内核
      → 逐模块 Shadow 迁移纯 Control
      → 通过无功率、时序、Break 和低压门禁
      → 得到单电机有感最小闭环
      → 清理 pm/common/Legacy，形成核心架构发布候选
      → 固化算法复现、离线回放、C-SIL/HIL 接口
      → 再独立扩展无感、辨识、自整定和其他高级能力

这条路线既保留现有算法资产，又能在每一步回答：

- 改了什么；
- 没改什么；
- 如何证明；
- 失败时退到哪里；
- 当前允许安全运行到什么范围。

本轮只输出方案，没有修改生产源码、工程文件和硬件配置。
